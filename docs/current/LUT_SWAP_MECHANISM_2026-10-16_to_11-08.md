# LUT 换表机制：从「成片死路」到「4 字节 + 半按」

> **2026-11-20 文档合并**：本文由 11 份记录按时间顺序合并，原文未删改、标题层级下调一级；原始文件归档在 `docs/archive/`，见各节「原文」。

## 机制演进（读这一节就够）

这条线一共错了四次，每次都把"不可能"改成"条件没满足"。按时间：

### 0. 起点：一个被外推过度的负结论（10-09）

U6 上机把 Portra 装进 LUT1，半按、松开、全按，成片没有风格；Still 期 `Cfg` 从 `0x0` 变成 `0x1100`。
据此写出 E4：**「成片直灌 LUT 是死路」**。后来的记录承认，这是把"某一条序列的负结果"外推成了机制结论。

### 1. 重启与假设：打算让 sel=0 保住 LUT0（10-16）

LUT 线解冻。方案是"改灌 LUT0 + 用守护阻止 p7 重灌"。复核时发现守护只恢复**选择配置**、
不重灌**内容**，而 p7 可以在 sel 恒为 0 时自己触发 Load —— 这条路有代码层缺口。

### 2. 第一个转折：打错了表（10-17）

实机只读取值：当前 Load 源是 **A17 `0x81115200`**（肤色表），而 10-09 的负片实验写的是 **A12
`0x810FD100`**（标准池）。于是"写了表画面不变"**不是**地址错、更不是换表不可行，而是
**从来没写到 p7 真正在用的那张表**。E4 的解读从这里开始翻转。

同一轮还补上了此前真正缺的一环：p7 启动时把整段已初始化数据从镜像地址搬到运行地址，
42 个候选槽都在这段复制范围内 —— 逐槽搜常量引用找不到填充者，不等于没有填充者。

### 3. 位定义钉死，登记表可信（10-18 上午）

两件基础事实在同一轮闭合：

- **`SelLUT = Cfg bits[5:4]`**，bit8 是 LUT0 格式位、bit12 是 LUT1 格式位。
  ⇒ E4 里那个 `0x1100` 其实是 **SelLUT=0**，与 T4 记录的"Still 用 sel=0"不冲突；
  此前"bit12=SelLUT 所以矛盾"的判断**撤回**。
- **三张静态登记表在运行时地址上可读，且与记录逐项一致**（View4 4/4、Still6 6/6、BV12 12/12）；
  所在 16 KiB 代码区与镜像 `0x380000` **逐字节相同**（md5 `eec72668…`，diff=0）。

⇒ 登记表不是黑盒，改它等于改 p7 的装载目标。

### 4. 决定性一步：4 字节 + 写槽 + 半按（10-18 下午）

不刷机、不改固件：

1. 改 **1 个 4 字节登记表项**（`View4[3]`），`load_addr` 由 `0x81115200` → `0x81119f00`；
2. 往空闲槽写 **19,712 字节**（4913 项全部 `255−R` 反相）；
3. 半按触发重载 ⇒ **取景器出现明显负片**（用户目视确认）。

四条同时成立：登记表所在页可写；p7 **每次 Load 都重读登记表项**（`cfg`/`sel` 全程不变，
只有 `load_addr` 变）；改一个 word 就能改硬件装载源；写进槽的内容**真被渲染**。
同日更早的 sel=0 后端路线当场作废 —— 改动更大，收益相同。

### 5. "装了不生效"的两次误判（10-19）

- **退出路径还原**：`lut.sh apply` 之后 p7 还没来得及装载，`lut.sh off` 已经跑完 ——
  三条退出路径里只有一条会保住结果。数据通路没坏，是自己把表还原了。
- **改错了登记项**：当时只改 `View4[3]`，而相机"屏幕色彩"开启、输出 sRGB，实际选的是
  **`View4[1]`**。修法 = 双登记项 + 正常事件重载，连续换表与 off 恢复实机通过。

切换通过 ≠ 色彩正确：紧接着发现导入表严重偏色，那是另一条线（见 `LUT_FORMAT_AND_INPUT`）。

### 6. 秒切：把"必须半按"也推翻（11-08）

`lut.sh apply` / `off` 现在自己完成 Load，面板点一张取景器立刻变。
旧结论「不能从 ARM 侧强制 reload，只能半按」**只对"裸写 `+0x00c` + 脉冲"成立** ——
当年漏了两个必要条件。

同日还有两笔：`nx_lutptr.arm set` 把 p7 的 **23 项档位指针表**（View4 + Still6 + BV12 整族）
整体指到 A18，录像**首帧**即用户表（连续录 4 分钟无异常）；闪屏用 **CORE RSZ_OUT1_EOF（irq 14）**
等帧结束再装载解决，**"一帧是物理下限"的结论撤回**。

### 当前机制（一句话）

p7 每次 Load 都重读登记表项 ⇒ 改登记表就是改装载目标；槽内容会被真实渲染 ⇒ 写 19,712 字节即可换表；
两者都可双向回滚，断电即恢复原状。

#### 1.2 关键事实（引用）

- **表格式**：4913 项 × 4B `{R,G,B,pad=0}`，索引 `((B*17+G)*17+R)*4`，**槽步长 `0x4D00`**（19712B）。
- **表池三处**：
  - **镜像内静态池**（`p7_full.bin`，VA `0x808847C0` 起，Block A 20 槽 + Block B 22 槽）——**可直接离线读写**；
  - **运行时池（View/Still）**：标准 `0x810FD100` / 黑白 `0x81101E00` / 电影 `0x81106B00` / 肤色 `0x81115200`（镜像外 BSS）；
  - **MCB 池**：`0x813D8800 / 0x813DD500 / 0x813E2200 / 0x813E6F00`。
- **一致性**：「标准」表在镜像静态池与运行时 `0x810FD100` **逐字节一致** ⇒ 静态池 = 运行时池的内容源（复制路径待精确定位）。
- **p7 只用 LUT0**（View/Still/MCB 的 `_load` 全 `sel=0`）⇒ 我们的表放 LUT1（`sel=1`）不被覆盖；抢回只改 `Cfg.SelLUT`（一个寄存器写）⇒ `lutsentinel` 恢复。
- **CMA 两个合法区**：`0x8f800000..0x94000000` / `0x94000000..0xa6000000`；事故黑名单 `0x94000000+0x5000`。

### 3. 新证据：整段初始化复制

在 `p7_a2.bin` 中找到以下原指令（地址均为 P7 代码地址）：

```text
80011620  ldr     r1, [pc, #0x138]  ; literal @80011760 = 8079BDC0
80011624  ldr     r2, [pc, #0x138]  ; literal @80011764 = 81006000
80011628  ldr     r3, [pc, #0x138]  ; literal @80011768 = 813EE4C0
8001162C  pld     [r1, #0xC0]

80011634  vstmia  r2!, {d0-d7}
```

复制关系：

```text
镜像 file [0x79BDC0, 0xB84280)
  装载地址 [0x8079BDC0, 0x80B84280)
        -- 启动复制 0x3E84C0 = 4,097,216 字节 -->
  运行地址 [0x81006000, 0x813EE4C0)

runtime = 0x80000000 + file_offset + 0x86A240
```

这不是推测的逐表复制，也不是依赖 ELF 段表的加载：镜像里有直接执行的批量复制循环。旧 T4 的“无槽首地址引用、无 ELF 段表 ⇒ 填充者不在镜像内”推断作废。

三项独立核对：

1. **真实历史 dump**：`dram_pools_256k.bin` 的全部 262,144 字节，与 A2 镜像 `[0x885DC0, 0x8C5DC0)` 完全相同，diff=0；不限于四张表。
2. **原指令仿真**：在 Unicorn 中执行 `0x80011620..0x80011640`，完整复制 4,097,216 字节并到达预期出口，diff=0。仅开启 VFP 并映射 RAM，无外部调用桩、无 MMIO；没有模拟全启动、缓存或 DMA。
3. **既有 C1 候选**：与 A2 仅 A12 槽内 13,901 字节不同；同样执行复制后，`0x810FD100` 的整槽 md5 为 `235ad45324c042d0bd4233513e1fca52`（候选 identity）。这证明候选在该复制流程下进入目标 RAM，不证明真机画面效果。

### 4. 修正 View / Still 调用链

T4 把 View 静态四档的转发链接到了 Still 条件选表。重新逐个核对尾跳转：

```text
View 静态：8009A3E8 -> 802B03F4 -> 8029BAA4 -> 80381B2C -> 803837D0
Still：    8009A3C8 -> 802B03D4 -> 8029BA84 -> 80381ABC -> 80382B30
View 动态：8009A408 -> 802B0414 -> 8029BAC4 -> 80381B4C -> 80383800
```

`0x803837D0` 静态叶函数本身不做亮度阈值计算，其 `(r1,r2)` 四种输入对应：`(0,0)→skin`、`(1,0)→cine`、`(0,1)→mono`、`(1,1)→std`。本轮在 A2 与 C1 仿真 RAM 中各执行四次，8/8 返回预期地址；C1 仅 std 所选表变为 identity。

`CBackend_3dlut_View::_load` 在 `0x8011E268` 检查条件，在 `0x8011E27C` 调静态选择器或 `0x8011E2DC` 调动态选择器，之后在 `0x8011E2B8` 调 `0x80179314(table, sel=0, …)`。因此“名为标准的池”不等于该次取景必定选它；静态、动态分支和实际输入都应分开留证。两个选择参数不直接等同用户菜单名称。

### 5. 直写负结果能说明什么

本轮对原件重新核验：

| 文件 | 实际长度 | 相对对应镜像区的差异 |
|---|---:|---|
| `dram_pools_256k.bin` | 262,144B | 0 |
| `dram_pools_after.bin` | **196,608B** | 0（不能当完整 256KB） |
| `dram_chk.bin` | 262,144B | 14,748B，全部在 std/A12 槽内，整槽与 `neg_test.bin` 一致 |
| `dram_final.bin` | 262,144B | 0；**整个 256KB 与初始 dump 一致** |

这支持“写后的 CPU 侧映射可见，最终完整还原”，还不能证明硬件消费了写入内容。日志中的“负片无变化”“半按后仍无变化”为当时人工观察，本轮没有新的画面证据。

尚未排除：

- **未选中 A12**：历史寄存器记录常见 `0x81115200`（A17）；这不是今天实验当时的同步快照，但足以说明不能默认当前用 A12。
- **没有实际重新装载所写表**：镜像中装载通过地址寄存器和启动脉冲把数据送入硬件。仅改 RAM 不会自动执行这些动作；半按也不能代替“选中了该表且重载完成”的证据。`+0x00C` 是 Load 源地址登记，不应解释为硬件持续查 RAM 的指针；`+0x010` 是 Save 地址。
- **可见性/同步条件不明**：写入探针用 `/dev/mem` 的 `O_RDWR`，没有 `O_SYNC` 或设备侧完成证据。所获内核源码 `arch/arm/mm/mmu.c:548` 对有效 RAM 页会依据 `O_SYNC` 选择映射属性；原包配置启用了 `CONFIG_ARM_DMA_MEM_BUFFERABLE`。该源码不等于当前运行内核身份，但说明跨进程读回不能独自排除 CPU/设备缓存可见性问题。
- 该次管线可能未启用/未选中相应 LUT bank。没有同场 OnOff/Cfg 与成功重载记录，无法由“没变化”区分这些情况。

故不采用“写入没效果 ⇒ 同值 PA 一定是副本 ⇒ 真表必在 CMA”的推理。启动 MMU 代码也包含初始 identity 映射；若要提出运行时 VA/PA 不同，需另给转换证据。CMA 第一区的表头扫描未命中，不能裁决这个问题：旧扫描器会静默跳过 mmap 失败区，也漏掉块边界匹配，且未记录完整扫描覆盖率。

### 6. 下一轮实验：先证实选表，再决定是否写

| 顺序 | 动作和产物 | 推进条件 / 判据 |
|---|---|---|

阶段判定：

- **C1 固件身份正确，RAM 仍是原表**：先查启动/恢复/再初始化是否经过已找到的复制循环；不推断管线支持与否。
- **RAM 为新表，当前选择的是另一张表**：修正实验目标或选择条件，不能裁决 C1/C3。
- **已确认新表被所测管线成功装载，预览变化而 JPEG 不变**：继续追 Still 的选表/重载路径，保留 E4 的既有负结果。
- **预览/JPEG 都随同一修改发生可复现变化**：机制通过，再进入受控运行时导入设计。

#### C3 的最小设计约束

输入带目标槽、表体/整槽长度、内容哈希与提交序号。先在有明确所有权的缓冲里完整准备表，再在 P7 已知的加载时机提交；失败保持旧表，并保存每槽原始基线。20KB 复制、CPU/设备可见性、DMA 完成、半按/全按后的再次选表必须分别验证。不能由 A2 标量通道成功直接推定大表交换可行。

### 1. Cfg 位定义（钉死）

`test_server/sysarch/lutapi.c`：

```c
#define R_CFG   0x004   /* bits[1:0]=SelCbCr_ch  bits[5:4]=SelLUT
                           bit8=LUT0 fmt  bit12=LUT1 fmt */
```

同文件 L852-854 的映射溯源：

```
SelCbCr_ch(p->+0x14)      -> Cfg bits[1:0]   ★色度通道选择
SelLUT(p->+0x10)          -> Cfg bits[5:4]   ★选哪张表
SetColorFormat(sel, +0x18)-> Cfg bit8/bit12  ★色彩格式
```

三个已观测值的验算：

| Cfg | bits[5:4] | bit8 | bit12 | SelLUT | 出处 |
|---|---|---|---|---|---|
| `0x100` | 0 | 1 | 0 | **0** | 常态 |
| `0x1100` | 0 | 1 | 1 | **0** | E4：Still 期 |
| `0x1110` | 1 | 1 | 1 | **1** | E1：`lutapi` sel=1 后 |

⇒ `0x1100` 与 `0x100` 的差是 bit12（LUT1 格式位），**不是选择位**。Still 全程 SelLUT=0，`U6` 与 `T4` 互相一致。

> 记入纪律：判 SelLUT **只算 bits[5:4]**；bit8/bit12 是各自 bank 的格式位，混用会得出「Still 用 LUT1」这种反向结论。

## 5. 运行态换表闭环：改登记表 + 写槽 + 负片判决（2026-10-18）

> 原文：`LUT_RETARGET_LIVE_2026-10-18.md`（已归档至 `docs/archive/`）

> **一句话**：不刷机、不改固件，改 **1 个 4 字节登记表项** 并往 **空闲槽** 写 19,712 字节，半按触发重载后取景器出现**明确的负片画面**；两条写入均可双向回滚，备份与镜像逐字节一致。
> **前置**：[Cfg 位定义与登记表回读](LUT_SWAP_MECHANISM_2026-10-16_to_11-08.md)（22/22 与 16KB diff=0）。

### 0. 结论（四层全部实证）

## 7. LUT 滤镜 UI 端口（2026-10-18）

> 原文：`LUT_UI_2026-10-18.md`（已归档至 `docs/archive/`）

> ⚠️ **2026-10-19 修订，本文部分内容已过时。**
> 退出面板**不再自动还原**（改为面板内「还原原厂」按钮）；`apply` 在 **A18 / A19 两槽间交替**。
> 下文中「退出 UI 自动还原」「apply 末尾调 reload」「半按判断加 `&& !lut_mode`」三处记述均与现行代码不符，
> 现行机制与原因见 [本文 §8](LUT_SWAP_MECHANISM_2026-10-16_to_11-08.md)。

> **一句话**：LUT 换表做成了 NXUI 的第三个模式，绑在 **EV+WiFi** 上，主菜单也有入口。与 filmlab 完全独立，可叠加。

### 0. 入口

| 入口 | 路径 | 说明 |
|---|---|---|
| **EV+WiFi** | `scripts/EV_MOBILE.sh`（→ `/opt/usr/nx-ks/EV_MOBILE.sh`，keyscan 槽位） | 启动 LUT UI（`nxui.sh lut`）；**不再起 telnet/FTP** —— 该职能已由主菜单 `IP: x.x.x.x [Telnet关]` 的 `telnet_toggle.sh` 接管。NXUI 未启用时只弹提示 |
| **主菜单 → 实用功能** | `gui_func.NX500` 新增 `button|LUT 滤镜|nxui.sh lut` | 静态菜单项 |
| 命令行 | `nxui.sh lut` | 等同 EV+WiFi 的 UI 部分 |

**为什么不新开一个独立可执行文件**：`menu.sh` / `EV_EV.sh` / `EV_AEL.sh` 三个入口已经全部转发 `nxui.sh`，再抢按键必然冲突。因此复用同一进程，只是换数据源和执行器。

### 1. 与 filmlab 的关系：不冲突，可叠加

| 层面 | filmlab | LUT |
|---|---|---|
| 数据通路 | `prefman`/`setusr` → PW 7 维标量 → p7 档位池 `0xdc..0xe2` | 3D LUT 表（A18 槽）+ 登记表 |
| 存储 | pref 分区 4 个 CUSTOM 槽 | p7 内存池 |
| 触发 | `seq 0x13B` | 半按 / PW 触发连带重载 |
| UI 模式 | `nxui.sh filmlab`（默认） | `nxui.sh lut` |

两者作用在不同层，**同时生效等于双重调色**——这是设计选择，不是 bug。UI 上以标题区分（`LUT / 3D 滤镜` vs `FILMLAB / 滤镜预览`）。

### 2. 三个安全设计

| 设计 | 实现 | 理由 |
|---|---|---|
| **半按不还原** | 半按只 `XUnmapWindow` 隐藏面板，不走退出路径 | 半按是为了让开画面拍照；若此时还原，照片就丢掉 LUT |
| **退出必还原** | `main()` 末尾 fork+exec `lut.sh off` | 相机不会被留在"表被改写"的状态 |
| **dry-run 只读** | `lut_mode && !live` 时 action 用 `status` 而非 `apply` | `apply` 是真写入，dry-run 不能碰 |

`off` 还原三样：`View4[3]` → A17、`Still6[6]` → 原厂、A18 槽 → 备份内容。备份在**首次写入前**由 `lut.sh begin`/`apply` 自动生成，后续 `apply` 用 `still-write`/`write` 模式**不覆盖**首次备份。

### 2.5 实测反馈修复（10:57）

首次上机后用户反馈"最初几次切换很快，多试几次就失效"。根因是两个 bug 叠加：

| # | 问题 | 后果 |
|---|---|---|
| 1 | `apply` 只写表 + 改登记表，**不触发 p7 重载** | 点按后画面不变，必须等半按 |
| 2 | **半按 = 关闭 UI**（`event0` code 125 → `close_requested` → `break` 退出），退出走 `lut.sh off` | 用户"点几下再半按"时，最后一次写入被还原 |

修复：

| 项 | 实现 | 验证 |
|---|---|---|
| `nx_regtabwrite.arm reload <addr>` | 照 p7 在 `0x804A5C44` 的写序：`OnOff→Pulse清→Pulse bit0→LUTA←addr→Cfg原值→Pulse\|bit8→Pulse清`，读回 `load_addr` 与 `Cfg` 双验证 | 上机 `RELOAD ok`，`load_addr` 立即变 `0x81119f00` |
| `lut.sh apply` 末尾调 reload | 成功打 `OK applied`，失败打 `WARN ... half-press once` | 连续 `warm33→identity17→neg` 三次均 `RELOAD ok` |
| `lut.sh off` 末尾 reload 回 A17 | 登记表回原厂**不够**——硬件 SRAM 里仍是上一张表 | `off` 后 `load_addr=0x81115200` |
| `nxui.c` 半按判断加 `&& !lut_mode` | LUT 模式下半按不再关闭/还原 | 代码级，待实测 |

**`off` 那条是最容易漏的**：只改登记表的话，硬件里仍是最后一张表，画面停在负片，看起来像"关不掉"。

### 7. ★ 面板"配方表不可用"事故与修复（2026-10-18 12:1x）

#### 7.1 现象

往 `looks/` 铺了 25 个 look 后，LUT 面板不显示任何条目，只有一句
"配方表不可用 · 请先导出配方"。同一句在配方模式和 LUT 模式共用，
所以看不出到底哪一边出错。

#### 7.2 定位

用 `--dry-run` 直接读加载器，绕开面板：

```sh
B=/opt/usr/nx-ks/nxui/nxui.arm
DISPLAY=:0 $B --root /opt/usr/nx-ks --recipes /mnt/mmc/filmlab/recipes.txt \
    --engine /opt/usr/nx-ks/filmlab.sh --dry-run --lifetime-ms 400
# READY ... recipes=68      ← 配方模式正常

DISPLAY=:0 $B --root /opt/usr/nx-ks --recipes /mnt/mmc/lut/list.rec \
    --engine /opt/usr/nx-ks/lut.sh --lut --dry-run --lifetime-ms 400
# READY ... recipes=0       ← LUT 模式空
```

`list.rec` 里有 25 行，格式也对。差别在**名字**：

```
samsung_A00|samsung_A00|0|0|0|0|0|0|0     ← 含大写
```

#### 7.3 根因（两层）

**第一层：`nx_key_valid()` 只允许 `a-z 0-9 _`。**
`A` 不在集合内 ⇒ 该行被拒。

**第二层（致命）：`nx_load_recipes()` 是整表作废语义。**
任一非法行 ⇒ `goto bad` ⇒ 返回 -1 ⇒ `count=0` ⇒ 面板显示"配方表不可用"。
**三个大写文件名，让 25 个 look 全部消失。**

⇒ 面板容量、`list.rec` 格式、`lut.sh list` 输出、`awk` 可用性、`recipes.txt`
（68 行全部合法）都逐一排除过，问题只在 key 字符集。

#### 7.4 为什么改不了文件名

`/mnt/mmc/looks` 在 exFAT 上，**大小写不敏感**：

```
mv: 'samsung_A00.bin' and 'samsung_a00.bin' are the same file
```

⇒ 靠改名规避这个 bug 行不通。必须改校验。

#### 7.5 修复

| 文件 | 改动 |
|---|---|
| `nxui_model.c` | `nx_key_valid()` 只拒绝结构性非法：`\|`、控制字符、空串、超长；**大写 / `-` / `.` / UTF-8 全部放行** |
| `nxui_model.c` | 所有拒绝路径改为 `RECIPE_BAD()` 宏，**打印 `文件:行号: 原因`** 到 stderr（如 `bad key 'x'`、`field 4 = 300 out of range 0..200`、`expected 9 fields, got 8`） |
| `nxui.c` | 空表文案按模式分叉：LUT 模式 → "滤镜库为空 · 见 /tmp/nxui.log 与 /mnt/mmc/looks"；配方模式 → "配方表不可用 · 见 /tmp/nxui.log" |

保留整表作废语义：宁可全空也不半解析，避免用残缺列表驱动相机。

### 8. 严重品红/绿偏色的根因：不是 bug，是选表（2026-10-18 12:2x）

#### 8.1 结论先行

用户实测后报告"几个配方出现非常严重的品红或绿色偏色"。逐一排除后，
**转换链路没有错**，是那些表**本身就是极端风格**：它们在中性灰上就带有
50–180 级的通道落差，灌进取景器自然整片偏色。

#### 8.2 排除的三个方向

| 假设 | 检验 | 结果 |
|---|---|---|
| 轴序错位（R/G/B 轴被置换） | 灰点附近求 3×3 响应矩阵，看是否退化成置换阵 | **18 张全部对角占优**，无置换 |
| 转换器把 13³ 转错 | 4 张与 PC 浮点参考逐字节比（maxdelta ≤ 1 LSB） | 一致 |
| 极端色格点被截断 | 统计 0/255 占比 | 仅 velvia50 达 2.7%，其余 < 1% |

⇒ 三者都不成立。剩下的解释只有"表的设计本身"。

#### 8.3 量化指标：灰轴最大落差

**定义**：输入中性灰 (v,v,v) 时，输出 `max(R,G,B) − min(R,G,B)` 的最大值（8bit 级）。
这是肉眼能直接看到的整体偏色幅度，与场景内容无关。

| 分级 | 落差 | 含义 |
|---|---:|---|
| safe | ≤ 12 | 正常胶片染色，肉眼视为"白平衡正常" |
| mild | 13–25 | 轻微色调，可用 |
| strong | 26–50 | 风格强烈，需配合题材 |
| extreme | > 50 | 整片偏色，日常不可用 |

### 1. 主因：退出即还原

`nxui.c` 末尾（686-701）：

```c
if (lut_mode && live) {
    if (lut_keep) { /* 写 /mnt/mmc/lut/state/keep */ }
    else { execl("/bin/sh", "sh", engine, "off", (char *)0); }   // ← 还原槽 + 两张登记表
}
```

而 `lut_keep` **只在一条路径上被置 1**（`nxui.c:548-553`，`/dev/input/event0` code 125 press）。其余所有退出路径都不置：

| 触发方式 | 代码位置 | `lut_keep` | 退出时 `lut.sh off` | 用户看到的 |
|---|---|---|---|---|
| 半按，走 **event0 code 125** | `nxui.c:548-552` | 1 | 否 | 生效 |
| 半按，走 **`EV_S1.sh`**（`touch /tmp/nxui-close`） | `EV_S1.sh:5` → `nxui.c:559-561` | **0** | **是** | 闪一下 → 复原 |
| 点"保存并关闭" | `nxui.c:410-419`（commit+close） | **0** | **是** | 永远不变 |
| 按 OK / Enter | `nxui.c:592-595`（commit+close） | **0** | **是** | 永远不变 |
| 点"关闭"、Esc、窗管关闭 | `nxui.c:366 / 589 / 585` | 0 | 是 | 设计如此 |

#### 1.1 为什么"保存并关闭"这条最致命

`choose()` 已经先 `apply` 并写好了槽 + 登记表，用户再用最自然的方式点"保存并关闭"确认 → `commit_requested=1, close_requested=1` → 等 apply 子进程结束 → `break` → **无条件 `lut.sh off`**：

```
A18 ← 备份 / View4[3] ← A17 / Still6 ← 原厂
```

p7 此刻才在半按里读登记表，读到的是已经回退的 A17 ⇒ 画面永远是原厂表。**而且这个循环会稳定重复**：下次进面板又 `begin` → 又 apply → 又 off。

#### 1.2 半按走的是哪条通道

- `EV_S1.sh` 是 NX-KS 的 **S1 单击槽位脚本**（`/opt/usr/nx-ks/EV_S1.sh`，keyscan 直接调），10-17 加入 `touch /tmp/nxui-close` 就是为了"半按关菜单"。
- `nxui.c` 同时另开一条 `/dev/input/event0` code 125。两条并存说明当时没确认哪条是真通道。
- 若 keyscan 对 `event0` 做了 grab，nxui 的 `ev_fd` 读不到任何事件（`open` 成功但不派发，代码里也没有失败日志），`lut_keep` 永远是 0 ⇒ **半按 100% 还原**。
- 现场判据：`cat /mnt/mmc/s1.log`。有 `nxui=1` 的行 = 走的是 EV_S1 通道。

### 2. 次因：指针不变时 p7 是否重载，没有实证

`lut.sh apply` 只做三件事：写 A18、`View4[3]→A18`、`Still6→A18`，**不触发 Load**（`:120-128`，注释里"reload 是禁区"）。

问题在于：
- 第一次 apply：`View4[3]` 由 A17 变 A18 —— 指针**变了**。
- 第二次 apply：`View4[3]` 已经是 A18 —— `nx_regtabwrite patch` 直接打印 `NOTE: already at target, nothing to write`，**4 字节都不写**。此时只有槽内容变。

本文 §5 的三次半按（步 3/5/8）**每次 `load_addr` 都发生了变化**，也就是说"指针变"这个条件一直成立。**"指针不变、只换内容"这条路径没有任何一次实证。**

如果 p7 的 View 装载路径对 `load_addr` 做了"不变则跳过"，那么第二次以后的切换就永远不会重新 DMA 表 ⇒ 与"只有第一次生效"完全吻合。

> 注：`do_reload` 的写序是从 `0x804A5C44` 反出来的 7 次无条件写，看起来不像有条件分支；但"函数被调用"与"函数被跳过"是两件事，静态无法定论。

### 3. 相机上线后的 5 分钟判别（按顺序做）

| 步 | 命令 | 期望 | 判什么 |
|---|---|---|---|
| 1 | `cat /mnt/mmc/s1.log \| tail` | 有 `nxui=1` 行 | 半按走 EV_S1（→ 主因 2 成立） |
| 2 | `sh /opt/usr/nx-ks/lut.sh status` | `VIEW4` 第 4 项、`load_addr` | 当前登记表与硬件装载源 |
| 3 | `lut.sh off; lut.sh apply portra400` **不用面板** | — | 绕开 NXUI |
| 4 | 半按一次，再 `lut.sh status` | `load_addr=0x81119f00` | 指针已改 |
| 5 | `lut.sh apply trix400`（**不清 off**）→ 半按 → `status` | 若画面不变且 `load_addr` 不变 ⇒ **指针不变不重载** | 次因定论 |
| 6 | 若步 5 无变化：`lut.sh off` → `apply trix400` → 半按 | 画面变 ⇒ 确认必须"指针发生跳变" | — |

判别 5 的关键：两次 `apply` 都指向 A18，`load_addr` 读数相同是必然的，**只能靠画面**。所以判据用两张悬殊极大的表（如 `trix400` 黑白 vs `velvia50`），不要用 A18/A19 那种 4% 差异的相邻表（旧教训）。

### 4. 修复选项

#### A. 最小修（1 行级）：给所有"想保留"的退出路径置 `lut_keep`
- `nxui.c:559-561`（`/tmp/nxui-close`）→ 加 `if (lut_mode) lut_keep = 1;`
- `nxui.c:416-418` / `592-595`（commit+close）→ 同上
- 保持"关闭/Esc/WM"仍然还原

代价：`/dev/input/event0` 若真的读不到事件也无所谓，因为 EV_S1 那条已经兜住。

#### B. 语义修（推荐）：把"还原"与"退出"解耦
- 面板退出**一律不还原**，只在显式点"还原原厂"时 `off`。
- 理由：LUT 是拍摄参数，不是 UI 状态；关面板就把照片风格改了，本来就反直觉。
- 代价：需要一个"还原"按钮，否则用户只能靠重启或命令行 `lut.sh off`。

#### C. 双槽交替（解决次因）
- 每次 apply 在 A18 / A19 之间轮换，登记表跟着跳，**每次切换都产生指针变化**，不需要赌 p7 的重载条件。
- 附带好处：不再"逐字节改写正被登记表引用的槽"（`LUT_WORKBUDDY_REVIEW §4` 提过的竞态）。
- 代价：A19 是原厂 `Still6[2]` 的目标槽，会话结束后没有备份，`off` 只能靠重启还原 A19。需要单独为 A19 建备份。

**建议组合：B + C**。A 是过渡（改一行就能验证主因）。

### 9. 半按"排水"：关面板时补跑最后一个未落地的选中

#### 9.1 触发点

上一轮回答「半按能不能直接保存并退出」时，逐行核到主循环里的一道闸：

```c
/* 旧 */
if (!child && (!queue.close_requested || queue.commit_requested) && (index = nx_queue_take(...)) >= 0)
```

`close_requested=1` 而 `commit_requested=0` 时，队列里**还没 dispatch** 的 apply 请求被直接丢弃。而 LUT 模式的 apply 在 `choose()` 之后要过 150 ms 防抖（`NXUI_DEBOUNCE_MS`，`nxui_model.h:7`）才 `start_child`。

于是最常见的手势——滑到最后一张、手指还没离开就半按——写进槽的是**上一张**，而面板上高亮的是最后一张。屏幕和槽不一致，且没有任何提示。

#### 9.2 改法

| 位置 | 改动 |
|---|---|
| `nxui.c` 全局 | 新增 `drain_on_close` |
| 主循环 | 关闭条件加 `(!lut_mode \|\| queue.desired < 0 \|\| queue.desired == queue.applied)`：LUT 模式下还有没落地的选中就先不 break |
| 主循环 | `nx_queue_take` 的那道 `(!close_requested \|\| commit_requested)` 闸去掉；启动时若已 `close_requested` 则置 `drain_on_close` |
| `poll_child` | `drain_on_close` 的那一跑无论成败都退出——面板此时已 `XUnmapWindow`，没有地方显示错误；失败等价于"没切换"，日志里有 `BACKEND ok=0` |

**FILMLAB 不受影响**：`drain_on_close` 只在 `lut_mode` 下置位，FILMLAB 的关闭仍然是"丢弃未落地的预览"（它的 preview 本来就不是承诺）。

最多只补跑一张：`nx_queue_select` 是覆盖式的（`nxui_model.c:132` 只留最后一个 `desired`），不会连锁。

## 11. LUT 秒切：取消半按快门（2026-11-08 实机定案）

> 原文：`LUT_INSTANT_SWITCH_2026-11-08.md`（已归档至 `docs/archive/`）

> **2026-11-14 补充（录像路径定稿）**：`apply` 现在先跑 `nx_lutptr.arm set`，把 p7 的 **23 项档位指针表**（View4 + Still6 + BV12 整族）整体指到 A18 ⇒ 录像**首帧**就是用户表，watcher 只作兜底。用户实测**连续录制 4 分钟无异常**；本地另测 8 s / 53.3 MB 文件正常收尾，`WAIT` 中断耗时 3.2 ms。仍未覆盖的只剩「更多帧率组合」与「快速状态竞争」。见 `scripts/lut.sh:330`、`VIDEO_LUT_AND_2K_2026-11-07.md` 顶部更正。
>
> **同日闪屏修复已验收**：只把 Acc 复位前移到日志前没有改善用户看到的闪屏。后续发现 **CORE RSZ_OUT1_EOF（irq 14）可用**：取景 `once` 等帧结束再执行原加载序列；录像 watcher 走原路径。独立黑白/彩色五次交替与正式面板切换，用户均确认无异常闪屏。同步超时返回 rc=9，不盲目启动 DMA。最终加载器 MD5 `dff55a370f0bf7076fea840111dd15c3`，三副本一致；回归八场景通过，原库 57 项、后端 21 项通过。**“一帧是物理下限”结论撤回。** 证据：`E:/NXWA/rea-evidence/20261108-lut-flash/`。修前备份：`/mnt/mmc/lut/_bak_cleanup_20261108/`；接入帧同步前备份：`/mnt/mmc/lut/_bak_framesync_20261108/`。

> **一句话**：`lut.sh apply` / `off` 现在自己完成 Load —— 面板上点一张，取景器立刻变，不用再半按快门。
> 旧结论「不能从 ARM 侧强制 reload，只能半按」**只对"裸写 `+0x00c` + 脉冲"成立**，因为我们当年漏了两个必要条件。

### 0. 结论

| # | 命题 | 证据 | 强度 |
|---|---|---|---|
| 1 | ARM 侧可以让 ISP 立刻重读 LUT 槽 | `nx_lutload.arm once` 后画面立即换表（黑白↔彩色反复验证） | ★★★ 目视 |

### 1. 为什么以前花屏

`3DLUT_API_GUIDE` §5 记的「裸写 `+0x00c` + 脉冲会花屏」是实测现象，但归因错了层次 —— 不是"ARM 侧不能写"，而是**写的东西不完整**。

p7 自己的 Load 入口是 `FUN_004a5c44` → `FUN_004a5e30`，QEMU 逐条实测的写序（`3DLUT_APPLY_PATHS_2026-10-08` §4.1）：

```
+0x000 <- OnOff = 1
+0x008 <- 0            bit0 先清
+0x008 <- 1            bit0 置（Acc）
+0x00c <- table        Load 目标地址
+0x004 <- SelCbCr/SelLUT/ch 使能
+0x008 <- 0x101        bit8 置 → DMA 启动
+0x008 <- 0x001        bit8 清 → 脉冲结束
```

早期的 `lutload.arm` 只做了中间两行（写地址 + 翻 bit8），漏掉 `OnOff`、`Acc` 和 `Cfg` 的通道位 —— 硬件拿不到完整的 Load 条件，于是画面崩。

**2026-11-08 新发现的一条**：QEMU 记录里最后一写是 `0x001`，但真实硬件上 **bit0 必须回到 0**。留 bit0=1 时画面会停在异常（彩色错乱/花屏），清掉立刻恢复正常。固件里另有代码在别处清它（息屏前后读到的 `Pulse` 都是 `0x00000000`），所以 QEMU 那段记录只是序列片段，不是终态。

> 方法论：QEMU 能给"写了哪些寄存器"，给不了"硬件最终要停在什么状态"。**终态必须上机取**。

### 2. 现成工具就是引擎

不需要新写工具 —— `test_server/lutpipe/nx_lutload.c` 里已经有完整正确的写序，而且比手工 `devmem` 强在两点：

| 能力 | 手工 devmem | nx_lutload.arm |
|---|---|---|
| 7 次写的时间窗 | 每次 open/close `/dev/mem`，几十毫秒 = 闪好几帧 | 单次 mmap 连续写，微秒级 |
| 是否等 DMA | 不等，写回就读 | `ioctl(EP_IOCTL_ACC_INTR_WAIT)` 等 `ACC_3DLUT_RD_FINISH` |
| 收尾复位 bit0 | 容易忘 → 画面停在异常 | `out:` 分支无条件 `r[2]&=~1` |
| 型号护栏 | 无 | `/etc/version.info` 必须是 NX500 1.12 |
| 并发 | 无 | `flock /tmp/nxwa_lutload.lock` |

它原本只服务录像 watcher（开录后补载首帧），顺带就是秒切引擎。

**本次唯一的代码改动**：地址白名单从 3 槽（A17/A18/A19）扩到 6 槽（A12/A13/A14/A17/A18/A19），让 `off` 也能 kick p7 刚选中的原厂槽。

#### 5.1 瞬时闪屏：帧结束同步修复

已知 Acc=1 留置会让画面异常，因此必须先排除软件扩大这一窗口的因素。
先将 DMA 等待返回后的复位放到日志前，但用户目视与原来一样，故不能把日志
认作本次闪屏的已确认主因。空等 RD_FINISH 三次均超时，未发现旧完成事件误报。
单独写槽不变画面；硬件加载才切换。LVR 的 irq 9/10 不到达，但 CORE irq 14/15/16
可收到周期帧结束事件（约 20 ms）。最终选择 RSZ_OUT1_EOF（14），在打开 Acc
之前等待帧结束，再连续执行既有 Load 写序。传输中不提前清 Acc。

独立同步工具五次黑白/彩色交替全部成功，用户反馈“没有看到异常闪屏”。接入正式
三副本后面板反馈“正常切换，没有异常闪屏”。这证明当前取景测试有改善，不能
扩展为所有拍摄模式/录像/帧率已覆盖。录像 watcher 显式不等待取景 EOF。

#### 5.2 面板侧的缓解：LUT 模式去抖 450 ms

LUT 的一次 apply 要写 19,712 B 槽再触发一次 DMA，逐格落地在快速滑动时就是
「一帧花屏 × 格数」。所以把去抖做成队列属性而不是全局常量：

| 模式 | 去抖 | 理由 |
|---|---:|---|
| FILMLAB | 150 ms | PW 七维只是标量直推，不写槽、不 Load，越快越跟手 |
| **LUT** | **450 ms** | 每次落地要写槽 + DMA，等用户停手再落一次 |

`nx_queue.debounce_ms` 默认 `NXUI_DEBOUNCE_MS`，LUT 模式在 `nx_queue_init` 之后
改成 `NXUI_LUT_DEBOUNCE_MS`。另外两条路径不再依赖常量：

- `nx_queue_select_now()`：OK / 保存并关闭是明确确认，直接 `due = now` 跳过去抖。
  原先写的是 `now_ms() - NXUI_DEBOUNCE_MS`，常量一改就会失准。
- **关闭面板时 `due = 0`**：用户已经用关闭动作确认了这一张，不必再空等 450 ms。

实机：快速连滑 3–5 格只切一次（用户验收「只切一次，可接受」），单点一格
慢半拍但不难受。
