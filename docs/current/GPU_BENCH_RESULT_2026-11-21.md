## 1. 成功运行的必要条件（缺一不可）

```sh
cd /tmp/nx-gpu
DISPLAY=:0 \
LD_PRELOAD=/usr/lib/libnative-buffer.so \
/opt/usr/nx-ks/busybox timeout -t 60 ./gpu_bench.arm 5
```

| # | 条件 | 不满足时 |
|---|---|---|
| 1 | **`DISPLAY=:0`** | `eglInitialize` 返回 `0x3008`（`EGL_BAD_DISPLAY`） |
| 2 | **`LD_PRELOAD=libnative-buffer.so`** | `libEGL.so.1: undefined symbol: native_buffer_get_bo` |
| 3 | 先 `eglCreatePbufferSurface` 再 `eglCreateContext` | `eglMakeCurrent` 死锁 |
| 4 | BSS ≤ ~512 KB | 2 MB BSS 时 `dlopen`/`dlsym` 阶段长时间卡死 |
| 5 | **所有输出走 `out()`，不用栈缓冲 + `emit`** | 卡死在第一条经栈缓冲区输出的语句 |

★ 第 3 条与用户探针完全一致（探针就是 surface 先、context 后）。
★ 第 4 条：相机常驻内存只剩 ~6 MB（`MemFree`），大 BSS 会让后续 `dlopen` 触发的内存分配进入直接回收。
★ 第 5 条最反直觉：`char b[160]` + 自写 `svc` 输出会卡死，换成 `out("常量")` 链立即正常。
   成因未查明（怀疑 `-nostdlib` 下栈数组与内联 `svc` 的寄存器约束冲突），但**规律可复现**：
   `b[160]` / `b[96]` / `pb[64]` 三处全部卡死，改掉后全部通过。

## 2. 实测数据（reps=5，取各段最小值，单位 μs）

```
BENCH,128,copy,  800,2799,1200,nz=65152
BENCH,128,mat,  1200,2800,1199,nz=65528
BENCH,128,lut,   800,3199, 800,nz=64896
BENCH,256,copy, 1600,4799,3999,nz=260608
BENCH,256,mat,  1200,5200,3999,nz=262108
BENCH,256,lut,  1199,6799,4000,nz=259840
```

`nz` = 回读非零字节数，只能描述输出分布。清屏留下的不透明 alpha、上一帧或错误 shader 都可能产生非零值；新版改为逐像素与 CPU 参考比较。

| 尺寸 | 操作 | upload | draw | read | 各段最小值之和（非整次实测） |
|---|---|---|---|---|---|
| 128² | copy | 0.8 | 2.8 | 1.2 | **4.8 ms** |
| 128² | mat | 1.2 | 2.8 | 1.2 | 5.2 ms |
| 128² | lut | 0.8 | 3.2 | 0.8 | 4.8 ms |
| 256² | copy | 1.6 | 4.8 | 4.0 | **10.4 ms** |
| 256² | mat | 1.2 | 5.2 | 4.0 | 10.4 ms |
| 256² | lut | 1.2 | 6.8 | 4.0 | 12.0 ms |

## 3. 解读

**① 三段成本结构（256² copy）**

```
upload 1.6 ms (15%)   draw 4.8 ms (46%)   read 4.0 ms (38%)
```

- **upload**：256 KB 用 1.6 ms ⇒ 约 **160 MB/s**，纹理上传不是瓶颈
- **draw**：128²→256² 像素量 4×，时间 2.8→4.8 ms 只涨 1.7×
  ⇒ 存在 **~1.4 ms 固定开销**（管线建立/提交）+ 约 **53 ns/像素**
- **read**：4 ms 回读 256 KB ⇒ 约 **64 MB/s**，比上传慢 2.5×，是 Mali 离屏回读的典型代价

**② 不回读可能降低成本，显示路径仍需单独测量**

原测试中的 upload/draw 最小值相加如下，仅为分段参考；未包含帧获取、格式转换、窗口合成与显示同步：

```
256² copy: 1.6 + 4.8 = 6.4 ms
128² copy: 0.8 + 2.8 = 3.6 ms
```

**③ LUT 比色彩矩阵贵在哪**

`lut` 除源图采样外，对 RGB 各查一次 1D LUT。三个独立输入索引不能仅靠把表合成二维纹理就变成一次等价采样。
矩阵近似的适用性取决于目标色彩变换，不能保证替代 LUT。

## 4. 与现有路径的关系

| 路径 | 256² 量级的成本 | 说明 |
|---|---|---|
| 现有缩略图**直切** | 148 ms | 含 IPC + 文件 IO + 起进程，不是纯计算 |
| 现有缩略图**冷转码** | 7.9 s | 主要是 libjpeg 解码 |
| **GPU 处理（含回读）** | **10.4 ms** | 原分段最小值之和；含上传、驱动及同步 CPU 成本 |
| GPU 处理（不回读） | 6.4 ms | 适合直接显示 |

★ 这些任务的输入输出不同，不能据此计算相册加速倍数。新版实测中，256² 完整往返的调用进程仍耗约 5.6–6.0 ms CPU；常驻纹理绘制段约 0.4 ms，均不代表全系统 CPU 或整个应用 CPU 为零。

## 5. 局限

| # | 项 | 说明 |
|---|---|---|
| 1 | 只测了 128²/256² | 512² 因 BSS 限制未测；4096 是 `MAX_TEX` 上限 |
| 2 | reps=5 仍偏少 | 数据有 ±200 μs 抖动，趋势可信、精值待加密 |
| 3 | 源图 256²，未测"大图→小图"降采样 | 真实取景帧量级需另测 |
| 4 | 未测"不回读"路径 | 需接显示合成，工作量更大 |
| 5 | 未与 CPU 同任务做同机对照 | 缺 `libjpeg` 之外纯缩放/矩阵的 CPU 基线 |
