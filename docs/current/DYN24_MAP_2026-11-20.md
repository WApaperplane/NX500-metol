# DYN24：p7 的 24 个 3DLUT 档位指针（2026-11-20 复查）

> 用户提问：DYN24 那 24 条各对应哪个视频档、表多长？先看看之前做过没。
> **做过一半，而且我们那份工具差一项。**

## 1. 之前做过什么

`docs/current/VIDEO_LUT_FIRSTFRAME_2026-11-07.md` —— 为了"开录首帧就带 LUT"，
在 p7 数据段找到这张指针表，写了 `scripts/lut/nx_lutptr.arm`
（`dump|save|set|check|restore`），把表里所有项一次改成 A18。

当时实测是**成功**的：`SAM_0335` 共 179 帧 / 7.16 s，首帧即用户 LUT，窗口内零跳变
（对照 `SAM_0334` 第 6 帧才切）。集成进 `lut.sh apply/off/status`（`VIDEOPTR` 行），
备份落 `/mnt/mmc/lut/state/lutptr.bak`。

## 2. 那次数错了：23 项 vs 24 项

工具里写死 `LUTPTR_BASE 0x80383A28 / LUTPTR_N 23`。今天把 p7 镜像那一段
（VA 0x803839E0–0x80383A90）整段打出来看：

```
0x80383a1c  e59f005c      ldr r0, [pc, #0x5c]   → 0x80383a80
0x80383a20  eaffffba      b
0x80383a24  810eea00      ← 第 0 项（我们的工具从下一项开始）
0x80383a28  81145800      ← 我们当成第 0 项
...
0x80383a80  8112d700      ← 最后一项
0x80383a84  e12fff1e      bx lr
```

⇒ 数组是 **0x80383A24 起、24 项 × 4B = 96 B**，紧随其后才是 `bx lr`。
11-07 的判断（"23 项 92 B"）把表头的第 0 项当成了前面函数的字面量池。

运行时读 `0x80383A24` 仍是 `0x810EEA00`（与镜像相同，不是活的游标），
而且这个地址能被当槽读出完整的 19,712 B —— **它就是一个槽**，不是标量。

**后果**：我们的 `nx_lutptr.arm` 一直只覆盖 23/24。p7 若选中第 0 项，
用户 LUT 就被绕过（正是这份工具要消灭的症状）。
RC5 的 `nx_regtabwrite.arm dyn-*` 写 24 项，**这一点它是对的**。

> 暂不改默认行为：23 项版本在实机上验过 179 帧，24 项版本与黑屏同期出现（见 §4）。
> 要不要动第 0 项，等 §5 的逐档实测有结论再定。

## 3. 表多长：24 个槽全部 19,712 B

`gamma/bin/nx_slotwrite.arm read <addr> <file>` 逐槽读回：

| 槽 | 地址 | 长度 | md5 |
|---|---|---|---|
| 0 | `0x810EEA00` | 19,712 | `a738160b…` |
| 1 | `0x81145800` | 19,712 | `de30c20c…` |
| 11 | `0x8113BE00` | 19,712 | `9dd7a095…` |
| A18 | `0x81119F00` | 19,712 | `4c0cc78c…`（= 原厂备份） |

19,712 B = **4913 × 4 B**，`{Cr, Cb, Y, pad}`，与 A18 完全同格式（17×17×17 的 3D LUT）。

所以"格式对不上导致黑屏"这条**不成立** —— 24 个槽是同一种表。

## 4. 因此：DYN24 全指 A18 不能解释黑屏

三条反证：

1. 11-07 已经这么干过（23 项全指 A18），录像 179 帧正常；
2. 24 个槽同格式、同长度；
3. 事故现场 `dyn-restore` 之后画面回原厂，但**当时 gamma 也是 FACTORY、A18 也已被改** ——
   黑屏与 `clean-log.policy=READY` 这个"半状态"同时存在。

更可疑的是 **gamma native 事务**：`nxl-gamma-reload.arm` 自己是
`native_queue_is_hardware_completion:false`（把曲线排进队就走，不等硬件确认）。
若 `$GAMMA log` 排了队却没被消费，ISP 就停在半写的 gamma 上 —— 那才是全黑。

**这条要证伪很简单**（二分）：

| 实验 | 只做 | 预期 |
|---|---|---|
| A | `lut.sh clean-log-prepare`（写 A18 + video_enable，**不跑 gamma**） | 若黑 ⇒ 问题在 A18/指针；若不黑 ⇒ 与它们无关 |
| B | `gamma-reload.sh log`（只跑 gamma，不做 prepare） | 若黑 ⇒ 锁定 gamma 事务 |

两个都在 `vlog.sh off` 之后做，随时可退。

## 5. 24 条 ↔ 档位：仍未解，但有了入手点

扫全镜像里所有 `ldr rX,[pc,#imm]`（含负偏移），落在这段地址的只有 **10 个引用点**：

| 指令地址 | 指向 | 槽 |
|---|---|---|
| `0x80383908` | `0x80383A30` | 3 |
| `0x80383970` | `0x80383A48` | 9 |
| `0x8038397C` | `0x80383A4C` | 10 |
| `0x80383984` | `0x80383A50` | 11 |
| `0x803839B4` | `0x80383A5C` | 14 |
| `0x803839BC` | `0x80383A60` | 15 |
| `0x803839E4` | `0x80383A6C` | 18 |
| `0x803839EC` | `0x80383A70` | 19 |
| `0x803839F4` | `0x80383A74` | 20 |
| `0x80383A1C` | `0x80383A80` | 23 |

其余 14 项只能通过**数组基址 + 索引**访问（同一段代码里就有
`cmp r10,#0x4b0 / blt`、`cmp r0,#0x46 / movle r2 / movgt r3` 这种按值二选一）。

⇒ 这张表不是"按档位号索引的数组"，而是**一段函数共用的字面量池 + 若干按条件选择的代码路径**。
要给出"第 i 项 = 哪个档"，得逐条追这 10 个引用点的调用者，或者做实测：

- 实测法（更快）：在每种拍摄档（P/A/S/M、各分辨率/帧率、智能滤镜档）下读
  "当前 LUT0" 寄存器，记下落到 24 项里的哪一项。
- 静态法：把 10 个引用点所在的函数边界找出来，看它读的其它常量（档位枚举）。
