## 机制演进

### 0. 切换修好之后才暴露的问题（10-19）

登记表修好、画面能变之后，用户报告导入的 `hp5`、`fuji400h` 等几乎全部严重偏色。
中性灰阶 + 色度方向 + 两个真实 LUT 对照确认：**链路里表的坐标顺序是 Cr、Cb、Y**，
而旧转换器直接按 RGB 存 ⇒ 红蓝互换、中性轴错位。

修法是重出候选（BT.601 全范围），用户目视确认 HP5 黑白正常、Fuji400H 颜色恢复。
边界：红蓝顺序与中性轴有实机证据，**精确色彩标定没做**，不能称为"经过测量的相机色彩配置"。

### 1. 机内修正与回归复核（10-25）

CrCbY 修到机内转换器；同时做色彩回归复核，确认不是所有表都错、也不是所有表都对。

### 2. 网格：为什么是 17³（10-31）

硬件/固件吃的是 **17³ native**；33³ 必须下采样，收益不抵损失。这条决定了 `cube2lut` 的烘焙目标。

### 3. 输入端怎么测（11-07）

3DLUT 在 JPEG 编码器**之前** ⇒ 拍一张 JPG 就能反推输入端特性；
`measure_tone.py` 从灰阶反解 gamma / 肩部 / 趾部。至此"输入是什么样的"不再靠猜。

当前存在两个独立问题：

1. **选表分支不匹配**：分享记录中，取景器 Load 源跟随 `View4[1]`；现行 `lut.sh apply` 调用的 `patch` 只改 `View4[3]`。新增 `patch1` 只是工具能力，尚未接进 apply。因此原先“写入成功但画面不变”有明确的软件解释。这不证明所有模式都走 `[1]`，也不证明 `[1]` 就是“黑白风格”。
2. **原来的 RGB 坐标解释缺乏依据**：`4913 × 4B` 的物理布局成立，不能由此推出三个字节代表 RGB。原厂表具有精确的 `(128,128,Y)` 中性轴，强烈支持 **两条色度轴 + 一条亮度轴** 的解释。当前 `cube2lut.c` 却在输入、输出两侧都直接使用 RGB；它与 PC RGB 参考逐字节一致，并不能验证相机所需的色彩语义。

**因此分享末尾“纯灰表不可能偏绿/偏粉，所以不是表格式”的排除论证不成立。** 该说法只适用于 RGB 数值或保持中性色度的正确转换；在 YCbCr 中令三个分量相等通常会引入色度。现有证据无需先假设“P7 部分初始化”就能解释偏色，但还不能排除同时存在加载或时序问题。

### 为什么灰表会变绿、白表会变粉

在带 128 色度偏置的 YCbCr 中，无彩色需要 `Cb=Cr=128`，亮度可以变化。[ITU-R BT.601-7](https://www.itu.int/rec/r-rec-bt.601-7-201103-i/en) 给出亮度和色差信号的定义。

仅作反例，采用 BT.601 系数的全幅模型，并假设三个字节为 `(Cb,Cr,Y)`：

| 写入三个字节 | 模型解码到 RGB（截断至 0..255） | 含义 |
|---|---|---|
| `(0,0,0)` | `(0,135,0)` | 绿 |
| `(64,64,64)` | `(0,132,0)` | 绿 |
| `(128,128,128)` | `(128,128,128)` | 中性灰 |
| `(255,255,255)` | `(255,121,255)` | 粉/品红 |
| `(128,128,255)` | `(255,255,255)` | 白 |

因为两条色度在这些例子中相等，交换 Cb/Cr 不改变结果。此表是**数学反例和诊断预测，不是相机矩阵或现场像素测量**；相机实际使用 BT.601/709、全幅/限幅等仍待确认。

本地 `bw_acros100.bin` 每项三字节相等，只能证明它是 **RGB 灰表**。若消费者按色度/亮度解读，它就不再保证灰色。换回原厂字节立刻正常，同样与这个解释相容，不能排除色彩语义错误。

### 主错误在生成器与加载器的接口

1. [`gen_luts.py`](../../tools/lutgen/gen_luts.py) 文件头明确把槽三个分量解释为 RGB；`build()` 第 467 行起枚举 RGB 网格，直接写 `apply_film()` 的 RGB 输出，没有 CrCbY 输入坐标转换和输出编码。
2. [`lut.sh`](../../scripts/lut.sh) 第 135 行起：`.bin` 分支直接交给写槽工具；只有 `.cube` 分支才调用转换器。因此新生成的 `.bin` 绕过了 19 日已修正的转换器。
3. [`cube2lut.c`](../../test_server/lutpipe/cube2lut.c) 现在的默认转换实际是 **CrCbY → RGB → RGB LUT → CrCbY**，并保留 `--legacy-rgb` 仅供历史复现。
4. [`19 日修复记录`](LUT_FORMAT_AND_INPUT_2026-10-19_to_11-07.md) 不只有文字：目录 `raw8/gates/lut/cube_regression_2026-10-19/` 保存了中性灰、色度方向、HP5、Fuji400H 的用户回答和实机导出。用户当时确认 HP5 为正常黑白、Fuji400H 严重偏色消失。

原生布局的工作约定为：

```text
输入坐标：Cr, Cb, Y
索引：((Y_index * 17 + Cb_index) * 17 + Cr_index) * 4
输出字节：Cr, Cb, Y, 0
格点：0,16,32,...,240,255
无彩色：Cr = Cb = 128；Y 可以变化
长度：19652 B + 末项重复 3 次 + 48 个 0 = 19712 B
```

本轮重跑 `audit_lut_coordinates.py`：原厂 A13、A17、A18 的 `(axis0=8,axis1=8,axis2=k)` 都 **17/17** 精确等于 `(128,128,level(k))`；A13/A18 历史实机快照与镜像逐字节相等。把三个字节命名为 RGB 后得出的“原厂蓝角点、白点、暗部色温”不能当 RGB 标定数据。

#### 为什么 identity 正常而其他表全部怪

恒等表 `T(a,b,c)=(a,b,c)` 无论三个坐标叫什么都会返回输入。因此 `identity17` 正常不能证明它们是 RGB，轴方向各自只改变对应字节也不能证明它们是 RGB。

假设一张 RGB 设计对三通道都施加曲线 `f`，却被 CrCbY 引擎消费，那么实际变成：

```text
Cr_out = f(Cr_in)
Cb_out = f(Cb_in)
Y_out  = f(Y_in)
```

对中性输入，Cr/Cb 本应始终在 128。曲线只要把 128 提到 139，就把两条色度都推成正值，画面变品红；将 128 压到约 98，就使两条色度变负，画面变绿。**这不需要自动白平衡参与。**

同理，今天的 Bhalf 在错误坐标下减半的是第三分量 Y，因此主要降亮度；`R=G=B` 的所谓黑白表则把 Cr、Cb 和 Y 绑成同值，不能保证无彩色，还会把亮度范围压窄。这与实机描述一致。

### 不能继续沿用的排除方法与标定

- **“机端文件/槽回读一致，所以表没问题”不成立。** 哈希证明字节送达，不证明字节的色彩语义正确。
- **“R=G=B，所以只能是 LUT 后段偏色”不成立。** 仅对 RGB 输出成立；CrCbY 黑白应固定前两分量为 128。
- 今天 [`mk_ycc.py`](../../tools/lutgen/mk_ycc.py) 只逐项转换输出，输入索引仍保持 RGB；且只提供 YCrCb/Y CbCr 两种排列，均非 19 日确认的 **CrCbY**。两张失败不能排除正确的 CrCbY 编译方式。
- 用 `preview_photos.py` 按 RGB 读取 `.bin`，展示的是设计意图，不是相机消费该文件的结果。对这种预览做 dHue、dSat、Lab 统计，不能直接证明实机色彩正确。
- 用 RGB 解释原生三星表来拟合 `sat_env`、`bconv`、蓝区上限等，坐标前提无效。恢复编码后应重新评估这些补丁，不能宣布它们是三星色彩特征。
- sRGB/AdobeRGB 是输出色彩空间设置，不等于 ISP 内部 LUT 三轴就是 RGB。OLED 也会影响选表分支；目前证据不能确定其完整后段变换顺序。
- PW 七维需先固定，否则与 LUT 叠加；但它不是上述坐标错误的替代解释。
- 另有一个较小的导出错误：旧 `write_cube()` 把硬件的非均匀 `0,16,...,255` 节点直接写成标准 `.cube`。标准 `.cube` 节点应为 `i/(N-1)`；不能把两种采样网格混用。本轮候选配套 `.cube` 已按均匀 33³ 重采样。

## 5. 17³ 能否扩到 33³（2026-10-31）

> 原文：`LUT_GRID_17_VS_33_2026-10-31.md`（已归档至 `docs/archive/`）

> 问题（木一）：**有没有可能把 17³ 扩大到现在比较主流的 33³。**
> 两条腿分开答：**硬件能不能**（静态证据）、**扩了值不值**（数值实测）。

---

### 0. 结论

| # | 命题 | 强度 |
|---|---|---|
| 1 | **硬件不可扩**：表长由 EP 的 DMA 控制器硬连线，p7 只写地址+脉冲，不写长度，也没有长度常量 | ★★★ |
| 2 | 槽池的几何本身反证 17³：103 个槽 × `0x4D00`，42 个槽各自是完整独立的表 | ★★★ |
| 3 | **对我们现有 12 张主表，33³ 的收益小于噪声**：均值 0.78–1.98 级，p95 1.8–5.4 | ★★★ 实测 |
| 4 | 对**强色相选择性**的表（导入的 Hasselblad 风格），17³ 损失达均值 7.7、p95 42，这时 33³ 才有意义 | ★★★ 实测 |
| 5 | 真需要 33³ 时，唯一路径是**成片后处理**（RAW → 33³ → JPEG），不是机内硬件 | ★★ |

---

### 1. 硬件：为什么扩不了

#### 1.1 固件里没有任何"尺寸"概念

对 `p7_a2.bin`（12,075,648 B）做小端字面量全扫：

| 常量 | 含义 | 命中 |
|---|---|---:|
| `19652` | 17³ × 4B 表长 | **0** |
| `4913` | 17³ 节点数 | 9（全在 `0x94011c` 一带，非 3DLUT 区，且 0x1331 是常见指令立即数） |
| `35937` | 33³ 节点数 | **0** |
| `143748` | 33³ × 4B | **0** |
| `215622` | 33³ × 6B | **0** |

⇒ **p7 连自己搬多大的表都不知道。** 它只写 `+0x00c` 地址 + `+0x008` bit8 脉冲，长度由 EP 硬件的 DMA 控制器决定。

#### 1.2 API 层也没有长度参数

```c
int d5_ep_3dl_load_lut(unsigned *addr, int sel, int fmt, int timeout);
```

四个参数，无 size、无 width/height。`d5_ep_lut_op_info_st` 里只有 `sel` / `fmt` / `cbcr_ch` / `bypass`。

#### 1.3 寄存器块只有五个

全镜像 grep `0x2082b`：

```
+0x000 OnOff   +0x004 Cfg   +0x008 Pulse   +0x00c LUT0 addr   +0x010 LUT1 addr
```

没有尺寸、没有步长、没有第二级。

#### 1.4 槽池几何反证

- 槽步长 `0x4D00` = 19,712 B
- 表有效 19,652 B + 尾部 60 B 指纹
- T1 实测：42 个槽**逐个都能完整读出**，每个槽尾部指纹都对得上
- 若硬件按 33³ 读（143,748 B），一个槽要吃掉 7.3 个槽位，42 个槽根本不成立；而且写 19.7 KB 后必然读到相邻槽的垃圾，画面会崩

**而实测写入 19,712 B 后，负片表渲染精确正确**（10-18 §1 第 8 步）。这是最硬的反证：硬件读的就是 19,652 B。

⇒ **17³ 是硬连线的。改 p7 也没用（它没有长度概念），只能改硬件。**

---

### 2. 数值：扩到 33³ 值不值

#### 2.1 方法

同一张 33³ 设计 → 编译到 17³ native 格点 → 用 `native_codec.sample_rgb` 走完整硬件路径（RGB→YCbCr→节点查表→RGB）→ 与 33³ 插值结果在 20,000 个随机色点上比较。

（**不**拿 `looks/*.bin` 直接比，因为那些表经过 `balance_neutral_axis` + `stretch_levels` 后处理，与 `rgb_design_cubes` 不是同一映射——第一次跑出 37 级的差异就是踩了这个坑。）

#### 2.2 我们自己的表

| 表 | mean | p50 | p95 | p99 | max |
|---|---:|---:|---:|---:|---:|
| kodak_portra400 | **0.95** | 0.71 | 2.53 | 4.50 | 7.8 |
| fuji_velvia50 | **1.98** | 1.43 | 5.35 | 7.80 | 20.9 |
| fuji_classicchrome | **0.78** | 0.63 | 1.83 | 3.47 | 10.7 |
| pentax_gold | **0.86** | 0.66 | 2.21 | 4.49 | 8.3 |

**均值不到 2 级，p95 在 2–5 级。** 参考量级：NX500 的传感器噪声在中间调约 2–3 级，JPEG 量化在平滑区也在这个量级。⇒ **对这批表，33³ 的收益被噪声吃掉，不值得。**

#### 2.3 导入的强风格表（对照组）

`_lutweb` 里的 33³ 公开胶片 CLUT：

| 表 | 性质 | mean | p95 | max |
|---|---|---:|---:|---:|
| S5IIS2V | 线性→Log（近可分离） | **0.40** | 0.95 | 3.1 |
| L-Log_to_Natural_VLog | log→log 曲线 | 2.73 | 10.7 | 45 |
| HBNat / hb_std | 强风格胶片 | **7.3–7.7** | 40 | 147 |

⇒ **损失完全由表的"色相选择性"决定**：平滑的曲线/矩阵映射在 17³ 上几乎无损（0.4 级），强色相旋转 + 局部饱和压缩在 17³ 上会丢 7–8 级。

#### 2.4 判据

要判断一张表需不需要 33³，跑一遍 `res_native.py`：

- `mean < 2` 且 `p95 < 6` ⇒ 17³ 够用
- `mean > 3` 或 `p95 > 10` ⇒ 33³ 有实际收益

### 3. 真要 33³，怎么走

| 路径 | 可行性 | 说明 |
|---|---|---|
| 改 EP 硬件尺寸 | ✗ | 无公开手册，无寄存器，API 无字段 |
| 改 p7 让其搬 33³ | ✗ | p7 没有长度概念，改了也没处写 |
| 双 LUT 串联模拟 33³ | ✗ | 上一轮已证硬件只有一级且串联有损 |
| **成片后处理（RAW → 33³ → JPEG）** | ✅ | `ksfilm.arm` 在相机侧跑，或 PC 侧；非实时 |
| 预览用 17³、成片用 33³ | ✅ | 与「双槽分发」天然契合 |

**最后一条是唯一有产品意义的组合**：取景器 17³ 够看（误差 1–2 级肉眼难辨），成片用 33³ 后处理拿满精度。前提是拍 RAW（SRW），否则二次 JPEG 处理会叠加压缩损失。

## 6. 3DLUT 输入曲线标定

> 原文：`LUT_INPUT_CALIBRATION_2026-11-07.md`（已归档至 `docs/archive/`）

日期：2026-11-07
工具：`tools/lutgen/measure_tone.py`（已用合成数据自测：真值 gamma 2.2 → 拟合 2.229）
相机：NX500 1.12（192.168.0.103）

### 为什么拍 JPG 就够，不需要 RAW

3DLUT 挂在 **ISP 末端、JPEG 编码器之前**。它看到的 8bit YCbCr 就是 JPG 里的像素值 —— 均匀色块下 DCT 量化误差 < 1 码。所以：

```
拍 JPG → 测像素码值 = 直接测 3DLUT 的输入端
```

不需要 RAW，不需要知道光源绝对亮度，也不需要辐射度标定。快门比例本身就是精确的 EV 标尺。

### 为什么必须实测

设计 LUT 只有三种起点：

| 做法 | 后果 |
|---|---|
| 凭感觉调（现状） | 单个场景好看，换场景就崩 |
| 假设机内是 sRGB / gamma 2.2 | 如果实际不是 2.2，所有 LUT 全盘偏，且偏得看不出来 |
| 实测本机曲线再反推 | 唯一可靠 |

`sensor + ISP + Picture Wizard` 串起来的实际曲线，没有公开数据，只能测。

### 拍摄协议

#### A. 前提（由我执行）

- `lut.sh off` —— **当前 `ACTIVE warm_gold`，不关掉测的就是 LUT 之后的曲线**
- 记录入场状态（LUT 名、WB、光圈、ISO）以便标定后恢复

#### B. 布光与靶（需要人做）

| 项 | 要求 |
|---|---|
| 靶 | A4 白纸或 18% 灰卡，**无纹理、无折痕**，平贴墙面 |
| 光 | 均匀：两盏灯 45° 交叉，或阴天窗光。**禁止单灯直射 / 闪光**，会出现热斑 |
| 相机 | 三脚架或稳定支撑，距靶约 0.8 m，靶面填满画面中部（脚本只取中心 34%） |
| 铁律 | 整个序列期间**不动灯、不动相机、不挪位置** |

#### C. 相机设置

```
档位      M
光圈      f/5.6          （不要用最大光圈，避免暗角）
ISO       100
白平衡    固定（按光源选区温），不要 AWB

尺寸      最大

```

#### D. 快门序列（16 张，1 EV 步进，约 90 秒）

```
1/4000  1/2000  1/1000  1/500  1/250  1/125  1/60  1/30
1/15    1/8     1/4     1/2    1       2      4     8
```

每张**只改快门**。顺序随意，但中途不能动灯或相机。

偷懒版：如果嫌 16 张多，隔一档拍 8 张（2 EV 步进，1/4000 到 8s），曲线形状仍能看出，只是肩部/趾部定位粗一倍。

#### E. 拍完当场自检

- 每张回放：中心应是一片**均匀**灰，看不到阴影、渐变、纸纹
- 最长曝光的 1–2 张应当**全白**（正常，高光裁切点需要它）
- 最短曝光的 1–2 张应当**很暗但不是全黑**

### 分析（由我执行）

拍完留在卡上即可，我拉回来跑：

```sh
python tools/lutgen/measure_tone.py <目录>
```

输出四个文件：

| 文件 | 内容 |
|---|---|
| `tone_samples.csv` | 每张：快门、相对 EV、RGB/Y 均值、均匀性、过曝比例 |
| `tone_curve.svg` | 曲线散点 + 线性段拟合线（浏览器直接打开） |
| `tone_lut.csv` | **0–255 码值 → 相对 EV 反查表**，`in_measured_range=0` 为外推值 |
| `tone_report.txt` | 结论摘要 |

报告给出：

- **等效 gamma**：线性段 `log2(Y)` 对 EV 的斜率倒数
- **线性段范围**：曲线真正按幂律走的 EV 区间
- **肩部压缩量**：高光端实测比线性预期低多少码
- **趾部抬升量**：暗端比线性预期高多少码（降噪/黑电平抬升的痕迹）
- **有效动态范围**：可用段跨多少 EV

### 判据

| 实测结果 | 含义 | 对 LUT 设计的影响 |
|---|---|---|
| gamma ≈ 2.2 | 机内接近 sRGB | 可以直接用 sRGB 假设起稿 |
| gamma < 2.0 | 曲线更平、对比度低 | 阴影段码值富余，LUT 可更激进压暗 |
| 肩部早压缩（< +0.3EV 就压 10 码以上） | 高光宽容度小 | 高光区 LUT 不要拉亮，只做色相修正 |
| 趾部抬升明显 | 暗部被降噪抹平 | 暗部色阶已被破坏，LUT 强行提亮会出色块 |

### 后续

拿到 `tone_lut.csv` 之后，才能做真正的「反推式 LUT 设计」：先指定目标曲线（比如某型胶片的 H-D 曲线），再用输入曲线反解出 3DLUT 该给每个输入码值施加的映射，而不是现在这样按感觉调对比度。

### 附：脚本可靠性

用合成数据验证过一遍：构造 gamma 2.2 + 肩部压缩的 15 档序列，脚本拟合出 gamma 2.229、肩部压缩 7.9 码，与解析计算（242.4 vs 实测 242）一致。
