### 0. ★ 五条一句话结论

1. **全镜像只有 7 个函数访问 3D LUT 寄存器块 `0x2082b000`**（穷举证据见 §1）——都是 40 字节以内的寄存器原语。
2. **唯一把表地址交给硬件的函数 = `FUN_004a5e30`**；`FUN_004a5c44`(Load) 与 `FUN_00179384`(Save) 是它的两个封装。
3. **5 条应用线路**：`View`｜`Still`｜`CS`｜`Base`｜**`MCB`（本次新发现）**。
   前四条是 C++ 虚方法（无 BL 调用者，走 vtable），第五条是 MCB 生产域的**打包序列**。
4. ★★ **寄存器语义修正**：`+0x00c` / `+0x010` **不是 LUT0/LUT1 两条通道**，而是
   **Load 目标地址 / Save 目标地址**；`+0x008` 的 **bit8 = Load 启动脉冲 / bit4 = Save 启动脉冲**（先置后清）。
5. ★★ **存在第二套表缓冲池**：View 档位池 `0x810FD100` 族之外，MCB 线路用
   `0x813D8800 / 0x813DD500 / 0x813E2200 / 0x813E6F00`（QEMU 实测逐条命中），**步长同为 `0x4D00`**。

### 1. L0 — 硬件入口穷举（为什么只能有 7 个）

p7 用 **`mov Rd,#imm12(rot)` + `movt Rd,#imm16`** 构造 MMIO 基址（**不是 movw，也不在字面量池**），
所以按寻常"搜 0x2082b000 字面量"会得到 0 命中（旧文档的盲区）。按指令位模式扫描后：

```
L0. 构造 0x2082b000 的位置 → 全部 7 个函数
   FUN_004cf3d4   OnOff            (+0x000 bit0)
   FUN_004cf3fc   Cfg[1:0]         (+0x004) SelCbCr_ch
   FUN_004cf414   Cfg[5:4]         (+0x004) SelLUT（值 = 通道号 0/1/2）
   FUN_004cf42c   Cfg[8]           (+0x004) ch0 使能
   FUN_004cf444   Cfg[12]          (+0x004) ch1 使能
   FUN_004cf45c   Pulse bit0       (+0x008) Acc 使能
   FUN_004cf484   ★ Pulse bit8/bit4(+0x008) **Load/Save 启动脉冲（先置后清）**
   （FUN_004cf4b4 用条件执行 `streq/strne`，按偏移写 +0x00c/+0x010，不构造基址）
```

⇒ **不存在"绕过这 7 个原语直接写 3D LUT 硬件"的代码路径**（判据：全镜像常量构造穷举）。

> ★ 与旧文档的差异：旧文只列了 5 个寄存器偏移，且把 `+0x008` 记作 "Pulse=0（无意义）"。
> 本次解出 **bit8/bit4 是启动脉冲** —— 它才是"把表推给硬件"的动作。

| `FUN_004a5ff0` | 配置通道使能与选择（**不搬数据**） | Cfg 位 + ch 使能 |
| `FUN_004a5b6c` | 描述符解析 → `FUN_004a5ff0` | 同上 |

| `FUN_004a5de4` | ch 使能写入器（mode 1/0/2） | `FUN_004cf42c/444` |

**p7 侧 API 对**（`0x179xxx` 区）：

| API | 底层 | 模式（QEMU 实测） | 锁 |
|---|---|---|---|
| `FUN_00179314(table,a2,a3,a4)` | `FUN_004a5c44` | **Load**（写 `+0x00c`，脉冲 `0x101→0x001`） | — |

| `FUN_001792c8()` | `FUN_004a5b6c` | 配置（不搬数据） | — |

⇒ **7 = Load 资源、8 = Save 资源**，与脉冲位 bit8/bit4 一一对应。

> ★★ **修正旧结论**：`P7_3DLUT_PATHS_2026-10-07.md` 把 `FUN_00179384` 描述为"load/save 封装"。
> 实测它是 **Save 路径**（mode=2）。View/Still/CS 三条线路用的都是 `FUN_00179314`（Load）。

### 3. ★ 五条应用线路

#### 3.1 线路 A/B/C —— 图像流水线（C++ 虚方法，走 vtable）

BFS 从种子向上回溯，**「无上游」节点恰为 4 个，全部是 `CBackend_3dlut_*` 类的虚方法**——
这正是铁律 117 的情形：**虚函数没有直接 BL 调用者，字符串 xref 恒为空**。

| 线路 | 入口 | vtable 槽 | 消息 ID | 选表函数 | 汇入 |
|---|---|---|---|---|---|
| **A View** | `CBackend_3dlut_View::_load` = `FUN_0011e20c` | `0x58385c` | `0x10000002` | `FUN_0009a3e8`(静态4档) + `FUN_0009a408`(动态24档) | `FUN_00179314` |
| **B Still** | `CBackend_3dlut_Still::_load` = `FUN_0011e678` | `0x58390c` | `0x20000002` | **`FUN_0009a3c8`**（专用，无动态分支） | `FUN_00179314` |
| **C CS** | `CBackend_3dlut_CS` = `FUN_0011ebbc` | `0x5839ec` | 同上二选一 | `FUN_0009a3c8` | `FUN_00179314` |
| **D Base** | `CBackend_3dlut_Base` = `FUN_0011d14c` | — | `0x10000001` 错误路径 | — | `FUN_001792c8`（仅配置） |

- **消息 ID 分流**：`0x?0000002` 走"材质描述路径"（`FUN_00176884` + `thunk_FUN_003f2428`），**不灌 LUT**；
  否则才走选表 + `FUN_00179314`。
- **`FUN_0009a3e8` 实测返回值**（QEMU S6，参数 `(fmt, cbcr)`）：

| fmt | cbcr | 返回表地址 | 档位 |
|---|---|---|---|
| 0 | 0 | `0x81115200` | 肤色 |
| 1 | 0 | `0x81106B00` | 电影 |
| 0 | 1 | `0x81101E00` | 黑白 |
| 1 | 1 | `0x810FD100` | 标准 |

（与伪代码逐条一致，纯查表无转换——**这条线路完全可离线预测**。）

#### 3.2 线路 E —— MCB 生产域（★ 本次新发现）

一段**打包好的完整应用序列**，位于 `0x3f2xxx / 0x3fbxxx` 区：

```
FUN_003f27ec  (0x3f27ec)  ← 调用者 0x175f94 / 0x176328 / 0x220590（应用层）
  └ FUN_003f222c (0x3f222c)
      └ FUN_003f3488 (0x3f3488)   ★ 3DLUT 应用打包
          ├ FUN_003fb1d4          MCB 准备（cmd 3）
          ├ FUN_003f2c60(r1=?, r2=idx)   ★★ 跳转表选表 → 装载
          │    └ 0x3fb4ac（参数胶水）
          │        └ FUN_003fb3b8(addr, sel, fmt)
          │            └ FUN_004a5c44 → FUN_004a5e30 → 寄存器
          ├ FUN_003fb368 → FUN_004a5b6c → FUN_004a5ff0   配置路径（不搬数据）
          ├ FUN_003fb51c → FUN_003f3fa4 族              MCB 寄存器读
          ├ FUN_003fb334                                MCB 系列操作
          └ FUN_003f56dc                                日志/事件
```

**跳转表 @ `0x3f2c70`（4 项，倒序）与对应的表地址**（QEMU 实测逐条命中）：

| idx (r2) | 跳转目标 | 字面量 | **表地址** |
|---|---|---|---|
| 1 | `0x3f2cc4` | `0x3f2cf4` | **`0x813D8800`** |
| 2 | `0x3f2cb0` | `0x3f2cf0` | **`0x813DD500`** |
| 3 | `0x3f2c9c` | `0x3f2cec` | **`0x813E2200`** |
| 4 | `0x3f2c80` | `0x3f2ce4` | **`0x813E6F00`** |
| 其他 | `0x3f2cd8` | `0x817D6AE4`（BSS 指针槽） | 运行时值 |

⇒ ★★ **这些地址在 BSS 区（> 镜像 0xC40000），是运行时缓冲**，
　且**四个地址两两相距 `0x4D00`** —— 与 View 档位池**完全相同的槽位粒度**，但**是另一组缓冲**。

> ⇒ **结论：3D LUT 至少有两套等距（0x4D00）表缓冲池**：
> 静态档位池（`0x810Fxxxx–0x8115xxxx`，给 View/Still/CS 用）
> 与 MCB 池（`0x813D8800–0x813E6F00`，给生产域用）。**此前只知前者。**

### 4. QEMU/Unicorn 复现（30 场景全部跑通）

**原理**：`p7_full.bin` 是 ARM 用户态 flat image，VA = 文件偏移 + `0x80000000`。
3D LUT 线路尾段是纯用户态代码（无 SVC / 无 MMU 依赖），
故可在 Unicorn 里直接执行，并在 MMIO 窗口挂写钩子，拿到**真实寄存器写序**。

#### 4.1 `FUN_004a5c44(table, sel=0, fmt=0, 0)` —— Load 完整写序（实测）

```
[0x2082b000] <- 0x00000001    OnOff = 1
[0x2082b008] <- 0x00000000    Pulse bit0 = 0
[0x2082b008] <- 0x00000001    Pulse bit0 = 1        ← Acc 使能
[0x2082b00c] <- 0x94000000    ★ Load 目标地址 = table
[0x2082b004] <- 0x00000000    SelCbCr = 0
[0x2082b004] <- 0x00000000    SelLUT  = sel
[0x2082b008] <- 0x00000101    ★ Pulse: bit8 置位    ← DMA 启动
[0x2082b008] <- 0x00000001    ★ Pulse: bit8 清除    ← 脉冲结束
```

#### 4.2 关键场景汇总

| 场景 | 输入 | 结果（实测） |
|---|---|---|
| `FUN_004cf484(1)` | — | `+0x008`: `0x100` → `0x00`（**Load 脉冲**） |
| `FUN_004cf484(2)` | — | `+0x008`: `0x10` → `0x00`（**Save 脉冲**） |
| `FUN_004cf4b4(a,b,1)` | — | `+0x00c` ← **a** |
| `FUN_004cf4b4(a,b,2)` | — | `+0x010` ← **b**（第 2 参，非第 1 参） |
| `FUN_004a5c44(t,sel,fmt,0)` | sel 0/1/2 × fmt 0/1 | 8–10 条写；`+0x00c`=t；`+0x004` 见 §4.3 |
| `FUN_004a5c44(t,3,·,·)` | sel=3 | `rc=-1`，**0 次寄存器写**（校验前置） |
| `FUN_00179384(t,0,0,0)` | — | ★ 写 `+0x010` + 脉冲 `0x11` ⇒ **Save 路径** |
| `FUN_00179384(t,3,·,·)` / `(t,0,2,·)` | 越界 | `rc=0xFFFFFFFF`，0 次写 |
| `FUN_00179384(t,2,·,·)` | sel=2 | 读未映射（**该 API 不支持 sel=2**，只构造 1 个描述符） |
| `FUN_0009a3e8(fmt,cbcr)` | 4 组 | 返回 4 档地址（见 §3.1 表）**逐条与伪代码一致** |
| `FUN_004a5b6c(&desc)` | ch=3 | `rc=-1`，0 次写 |
| `FUN_003f2c60(·,·,idx)` | idx 1..4 | ★ 写 `+0x00c` = **0x813D8800 / 0x813DD500 / 0x813E2200 / 0x813E6F00** |

**传参证据链（S8 实测，来自函数入口钩子）**：
```
FUN_003f2c60 → 0x3fb4ac(r0=0x94000000, r1=0x813d8800)
             → FUN_003fb3b8(0x813d8800, 0, 0)
             → FUN_004a5c44(0x813d8800, 0, 0, 0)     ★ 表地址确认为 0x813d8800
             → FUN_004a5e30(&desc@0x7f7fffc8)
             → FUN_004cf4b4(0x813d8800, 0x81792ab8, 1) → +0x00c
```

#### 4.3 `fmt` 的实测语义（不是"采样格式"）

| sel | fmt=0 | fmt=1 |
|---|---|---|
| 0 | `+0x004` = `0x00000000` | `+0x004` = `0x00000100`（bit8 = ch0 使能） |
| 1 | `+0x004` = `0x00000010` | `+0x004` = `0x00001010`（bit12 = ch1 使能） |
| 2 | `+0x004` = `0x00000020` | `+0x004` = `0x00001120` |

⇒ `fmt` 被写进描述符 `+8` 字节，最终由 `FUN_004cf42c/444` 落到 **Cfg 的 ch0/ch1 使能位**。
　（旧文档称 `fmt` 为 "420/422 采样格式"——**实测是"通道使能"语义**。）

## 2. 3D LUT 表格式 —— 解开（2026-10-08 · R1 主成果）

> 来源：`3DLUT_TABLE_FORMAT_2026-10-08.md`（已归档至 `docs/archive/`）

> **实机色彩顺序已闭合（10-19）**：中性灰阶与色度方向对照支持输入轴/输出字节为 Cr、Cb、Y；按此重采样 HP5 与 Fuji400H，用户确认严重偏色消失，见 [CrCbY 修复](LUT_FORMAT_AND_INPUT_2026-10-19_to_11-07.md)。下文 RGB 命名按历史证据保留，不再用作生产转换约定。

> **2026-10-19 色彩语义复核**：本文的 `4913×4B`、槽步长与字节布局证据仍有效；把三个字节和输入轴直接命名为 RGB 的结论需要修正。原厂 A13/A17/A18 全部具有精确的 `(128,128,Y)` 中性轴，见 [LUT_COLORSPACE_AUDIT_2026-10-19.md](LUT_FORMAT_AND_INPUT_2026-10-19_to_11-07.md)。不要把 pad 恒零或 RGB 参考输出一致当成硬件 RGB 语义已验证。

> 承接 本文 §3 §6 的 **P1（解出表格式）** 与用户指令 **「先走 r1，再试 r3」**。
> **本文只回答三件事：表格式是什么 / 表在哪 / 旧结论哪几条被否。** 全程离线，零上机、零风险。

### 0. 一句话

**表格式 = 4913 项 × 4 字节 `{R,G,B,pad=0}`（24-bit RGB + 空字节），索引 `((B*17+G)*17+R)*4`（R 最快），槽步长 `0x4D00`。**

- `p7_full.bin` **文件内**就有完整的表池：**Block A（20 槽）+ Block B（22 槽）**，可离线逐字节读取。
- 其中「**标准**」表与归档里运行时 `0x810FD100` 的采样**逐字节一致** ⇒ 打通了「镜像内表池 ↔ 运行时缓冲」。
- **旧「16-bit 三通道交织」假说被否**（若为真，每 4 字节的第 4 字节不可能恒为 0）。
- ⇒ **P1 的「save_lut dump 是唯一直接路径」表述作废**；dump 降级为**交叉验证**手段。

---

### 1. 表格式（逐字节自证）

#### 1.1 原始字节（`p7_full.bin`，VA = 文件偏移 + `0x80000000`）

| 槽 | 前 16 字节（hex） | 解读 |
|---|---|---|
| `0x808847C0` | `08 08 10 00 · 17 08 10 00 · 26 08 10 00 · 35 08 10 00` | R 步进 +15/16，G=8 固定，B=16 固定，pad=0 |
| `0x8088E1C0` | `01 01 01 00 · 10 01 01 00 · 20 01 01 00 · 30 01 01 00` | R = 16 进制的 1,16,32,48…，pad=0 |
| `0x80897BC0` | `00 00 00 00 · 10 00 00 00 · 20 00 00 00 · 30 00 00 00` | **纯 identity** |
| `0x80892EC0` | `15 00 0d 00 · 23 00 0c 00 · 31 00 0b 00` | **标准**（见 §5） |

⇒ 每项就是 `{R, G, B, 0}` 四字节；第 4 字节（pad）**在整个表内恒为 0**（见 1.2 的自证）。

#### 1.2 三条独立自证

1. **pad 恒零**：对 4913 项逐项检查 `byte[4i+3] == 0`，命中表中 **100% 成立**（Block A/B 共 42 个槽全部通过）。
2. **单轴展开**：沿 R 轴（索引 `r`）、G 轴（`17g`）、B 轴（`289b`）分别取 byte0/byte1/byte2，三条 ramp 各自连贯；
   例如 `0x8088E1C0` 的 R-ramp =
   ```
   1, 16, 32, 48, 64, 80, 96, 112, 128, 144, 160, 176, 192, 208, 224, 240, 254
   ```
   ⇒ 输入 17 个**等距**电平（0,16,32,…,240,255），输出近似 identity（0 端抬到 1、255 端收到 254）。
3. **中性点**：`diag(i)=((i,i,i))` 对 identity/near-id 表在 i=8 处 = `(128,128,128)`（严格中性）。

#### 1.3 索引与电平

```
N            = 17³ = 4913 项
offset(i)    = ((B*17 + G)*17 + R) * 4      // R 变化最快
item         = { R_out, G_out, B_out, 0 }
输入电平      = 17 个：0, 16, 32, …, 240, 255（step 16）
占 用        = 4913 * 4 = 19652 字节
```

**索引公式的独立佐证**：`p7_full.bin` 内存在 32-bit 常量 `4913`(=17³) 于 `0x94011c, 0x954fac, 0x95524c`（3 处）——均位于**字面量池/数据段**，不在任何函数体内。

### 2. 槽布局与尾部填充

```
每槽 = [ 表 19652B ] [ 填充 60B ]          ← 合计 19712 = 0x4D00
填充 = 最后一项 ×3（12B） + 48×0x00
```

实测（`0x808847C0 + 19652` 起 60 字节）：
```
b6 b6 fe 00 | b6 b6 fe 00 | b6 b6 fe 00 | 00×48
```
⇒ 「最后一项重复 3 次 + 48 个 0」是本格式的**强指纹**，可作槽边界判据。

### 3. 镜像内表池（Block A / Block B）

锚点经 `0x80892EC0 % 0x4D00 = 0x6C0` 反推确定；两块的跨度都**精确等于步长的整数倍**：

| 块 | phase | VA 范围 | 跨度 | 槽数 |
|---|---|---|---|---|
| **A** | `0x6C0` | `0x808592C0 … 0x808B49C0` | `0x5B700` = **19.000×0x4D00** | **20** |
| **B** | `0xAC0` | `0x808B9AC0 … 0x8091EBC0` | `0x65100` = **21.000×0x4D00** | **22** |

#### 3.1 Block A（20 槽，phase 0x6C0）

前 12 槽以 **3 循环**重复：`[lift(8,8,16), lift(16,16,16), near-id(1)]` × 4，随后：

|---|---|---|

| `0x8085DFC0` | (16, 16, 16) | lift 黑位、均匀 |
| `0x80862CC0` | (1, 1, 1) | near-identity |
| …（×4 循环）… | | |
| `0x80892EC0` | **(21, 0, 13)** | **标准** |
| `0x80897BC0` | (0, 0, 0) | **identity** |
| `0x8089C8C0 / 0x808A15C0 / 0x808A62C0` | (21, 0, 13) | **标准** ×3 |
| `0x808AAFC0 / 0x808AFCC0 / 0x808B49C0` | (0, 0, 0) | identity ×3 |

#### 3.2 Block B（22 槽，phase 0xAC0）

```
0x808F36C0 标准 | 0x808F83C0 identity
0x808FD0C0 标准 | 0x80901DC0 identity
0x80906AC0 标准 | 0x8090B7C0 identity
0x809104C0 标准 | 0x809151C0 identity
0x80919EC0 标准 | 0x8091EBC0 identity
```

#### 3.3 假设（待上机证伪，勿当结论）

- **A / B 两块可能对应 LUT0 / LUT1 两个数据源**——寄存器 `+0x004` 确有 `bit8=SetColorFormat_LUT0`、`bit12=SetColorFormat_LUT1`（见 `3DLUT_API_GUIDE`）。
- 两块内「标准 ×N + identity ×N 交替」符合「**4 静态档 + 24 动态档**」的成对占位（`FUN_0009a408` 的 24 指针 + `FUN_0009a3e8` 的 4 指针）。
- ⇒ **精确的槽↔档位命名必须靠上机 dump**（见 §7 遗留）。

### 4. 与运行时地址的桥接（★ 关键）

三条独立证据把「文件内表池」与「运行时缓冲」连起来：

1. **步长同一**：
   - 4 个静态档缓冲 `0x810FD100 → 0x81101E00 → 0x81106B00 → 0x81115200`，相邻差 **`0x4D00 / 0x4D00 / 3×0x4D00`**。
   - MCB 池 `0x813D8800 / 0x813DD500 / 0x813E2200 / 0x813E6F00` 相邻差 **`0x4D00`**。
   - ⇒ `0x4D00` **确实**是 3D LUT 槽步长，而非巧合。
2. **内容同一**：归档 `EP_3DLUT_WRITE_EXPERIMENTS` 记的运行时 `0x810FD100` 前 8 字节 `15 00 0d 00 23 00 0c 00`
   **逐字节等于**文件内 `0x80892EC0` 的前 8 字节 ⇒ 运行时「标准」= 文件 `0x80892EC0`。
3. **常量佐证**：`0x4D00`(=19712) 以 32-bit 常量出现于 `0x9c9084, 0xa3674c, 0xa36efc, 0xa5cbbc`（4 处，均在字面量池）。

> **注意**：运行时缓冲 `0x810FD100` 的地址**超出文件**（`0x810FD100-0x80000000 = 0x10FD100 > 0xC40000`），
> 归档「表数据不在文件里」**对那 4 个运行时地址仍然成立**；但文件在 **`0x80859xxx–0x8091xxxx` 另存了一套表池**。
> ⇒ 两者是「**模板 / 副本**」关系，不是同一块内存。

## 3. View / Still 隔离性与「显示正常 + 成片有效」的解法（2026-10-08）

> 来源：`3DLUT_VIEW_STILL_ISOLATION_2026-10-08.md`（已归档至 `docs/archive/`）

> ⚠️ **2026-10-18 文档清理：本文结论已被取代。** 文中「View 与 Still 共用缓冲池 ⇒ 软件层无法隔离」已**部分推翻**：池确实共用（`View 4 档 ⊆ Still 18 档`），但三张登记表是分开的 —— 改 `View4` 只影响取景、改 `Still6` 只影响成片，2026-10-18 实机实证。
> 现行结论见 [`LUT_RETARGET_LIVE_2026-10-18.md`](LUT_SWAP_MECHANISM_2026-10-16_to_11-08.md)。


> 问题（木一）：**已确定 View 与 Still 不走同一条线，如何保证 LUT 在正常显示的前提下，且拍照成片有效？**
> 本篇用**穷举证据**回答：这个问题的前提需要被修正 —— 两条线**软件层面无法隔离**，
> 而"分离"本身**不是目标**。真正缺的是**表格式**。
> 附：本次新发现一条 **dump 内置表**的通道（save_lut），是解开表格式最直接的路径。
> 全程离线，未触碰相机。

### 0. 一句话结论

1. ★★★ **`View 4 档 ⊆ Still 可达集`，View 独有 = 空**（§1 穷举证据）
   ⇒ **在不改 p7 的前提下，"让两条线各走各的表"不可能**。
2. ★★ **「取景器花屏」的根因不是"挂错线路"，而是"表格式未知"**。
   ⇒ 表格式一旦正确，**View 与 Still 共用同一个池反而是优点**：一张正确的表放进档位槽，
   取景器正确 + 成片正确 = 真正的所见即所得。
   ⇒ **所以目标不是"分离两条线"，而是"解出表格式"。**
3. ★★★ **本次新发现**：p7 自带 **save_lut 通道**（把硬件里的表读回 DDR），
   且**目标地址由调用者指定**（`0x179520` 的 r0）——
   而 p7 能访问 Linux CMA ⇒ **可以在 Linux 侧读到内置表的原始字节**，
   不需要 `/dev/mem`、不需要读 p7 内存、不需要重刷固件。
4. **交付态有两条**：正式解 = 解表格式（所见即所得）；保底解 = 软件后处理（取景器不动）。

### 3. ★★★ 新发现的攻坚手段：save_lut 通道（dump 内置表）

#### 3.1 通道结构（静态实读）

```
0x179520  save 对外封装
  ├ 校验：r0(目标地址) != 0 且 第 5 参(sp+4) != 0 且 未占用（否则返回 -1）
  └ b 0x1794a8                        ← 尾调用
       └ FUN_0017b570(8)              ← 加锁（8 = Save 资源）
            └ FUN_00179384(dest, sel, fmt, ptr)
                 └ FUN_004a5e30(&desc)  mode=2
                      ├ 写 +0x010 = dest        ★ Save 目标地址
                      └ 写 +0x008 bit4 脉冲     ★ 触发 3DLUT → DDR 搬运
```

**QEMU 实测对照**（`FUN_00179384(0x94000000,0,0,0)`）：
```
[0x2082b000] <- 0x00000001
[0x2082b008] <- 0x00000000
[0x2082b008] <- 0x00000001
[0x2082b010] <- 0x94000000      ★ Save 目标地址 = 调用者给的
[0x2082b004] <- 0x00000000
[0x2082b008] <- 0x00000011      ★ bit4 置位（Save 启动）
[0x2082b008] <- 0x00000001      ★ bit4 清除（脉冲结束）
```

#### 3.2 为什么这条通道能解开表格式

| 约束 | 是否被绕过 |
|---|---|
| Linux 读不到 p7 内存（`/dev/mem` Bad address） | ★ **绕过**：不需要读 p7 内存 |
| Linux 写不到 p7 内存 | ★ **绕过**：只读，不写 |
| 需要重刷 p7 固件 | ★ **绕过**：走 p7 自带的官方 save 路径 |
| 需要知道表格式才能 dump | ★ **绕过**：dump 是"照抄字节"，**不需要懂格式** |

**充要条件只有一条**：`dest` 指向一块 **Linux 侧可读、p7 侧可写** 的内存。
→ **Linux CMA（`0x94000000–0xA6000000`）正好满足**（p7 identity 映射 4GB，见 `3DLUT_DEEP_DIVE` §6）。

⇒ ★★★ **执行方案**：
1. Linux 侧在 CMA 分配一块 ≥ `0x4D00 × 2` 的缓冲，取物理地址 `P`（例如 `0x94000000`）
2. 触发一次 p7 的 `save_lut(dest=P, sel=0)`，把内置档位表读回
3. Linux 侧读 `P` 起的 `0x4D00` 字节 ⇒ **内置表的原始字节**
4. 对比"标准档 vs 黑白档 vs 电影档 vs 肤色档"的差异 ⇒ **直接解出索引/通道布局**

**这是 7 张自造表全部失败之后，第一次有机会看到"正确答案长什么样"。**

#### 3.3 唯一待解问题：如何从 Linux 触发 save_lut

`0x179520` 的直接调用者尚未定位（它在 `0x1794a8`–`0x1795ec` 之间的 Ghidra 未识别区）。
已知线索：
- MCB 侧另有入口：`FUN_003fb4cc`（构造 `{2, b[0x4d], 0xff, 0xff, b[0x4e], 0xff}` → `FUN_004b7a40`）
  ← 由 `0x3fb5f8` 调用（同属 `0x3fbxxx` MCB 族）
- MCB 通道**实测是通的**（`st cap iqr` / `st cap capdtm` 均能工作，走 SHELL_COMMAND `0xb6`）

⇒ 下一阶段静态任务：**定位 3DLUT save 的 MCB 命令号**（在 68 条命令表里找 PRD_ / SYS_ 域的对应项）。

### 5. ★ 开发期策略：用 View 当探针，用 Still 当验收

由于 `View ⊆ Still`，**同一张表对两路都生效**，这带来一个高效率工作流：

| 阶段 | 平台 | 原因 |
|---|---|---|
| **格式探索** | **View** | ★ 实时反馈：改表 → 取景器**秒级**可见，不用拍照、不用读卡 |
| **格式确认** | View | 取景器颜色正常 ⇒ 格式对了 |
| **最终验收** | **Still** | 拍一张看成片（最严判据：照片是否真被处理） |

⇒ **顺序**：先在 View 上调对格式（允许开发期暂时花屏）→ 格式正确后取景器恢复正常
→ **同一张表自动对 Still 生效**（共用池）→ 成片自然有效。

★ **交付态**（表格式正确后）：显示正常 + 成片有效，**同时满足**。
★ **探索期**（格式未对）：显示会异常 —— 这是开发的必经阶段，不是交付缺陷。
