### 二、方法

#### 结构口径（纯格点，不需照片）

九项指标，阈值全部对 `identity17` 校准 —— **identity 必须九项归零**，
否则说明判据本身错了。首版就翻过车：暗部统计误用了格点序号而不是数值，
把 identity 判成 16.6% 压死。

| 指标 | 含义 | 阈值 |
|---|---|---|
| mono | 灰轴 / R 轴 luma 下降沿数 | >0 即硬伤 |
| black_luma | 输出 (0,0,0) 的 luma | >30 灰雾 |
| crush% | 输入三通道全 >0（且亮度≥20%）但输出某通道 =0 的比例 | >3% |
| white% | 输入三通道全 <255 但输出某通道 =255 的比例 | >3% |
| jump | 相邻格点输出最大分量差 ÷ 16 | >5.5 |
| gray | 17 个灰点输出的 max-min | >30（暖调表豁免） |
| dr | 灰轴 0→255 的 luma 落差 | <205 |
| hue | 六主色格最大色相偏移 | >45° |
| warm_r | 暖区格点 R/G 比值变化（参考值，不判定） | — |

#### 观感口径（真实照片，16 张）

**判"偏红"必须看色相位移 dHue，不能看 R/G。** 这是本次最重要的方法修正：

| 表 | dRG | dHue | 真实性质 |
|---|---|---|---|
| `fuji_velvia50` | +0.27 | **-1.8°** | 只是更饱和，色相没动 |
| `kodak_kchrome25` | +0.34 | **-7.6°** | 真把肤色推红了 |

两者 dRG 同量级。任何 `sat > 1.0` 的表都会在暖色像素上抬高 R/G，那是"更饱和"。
判据：hue∈[0,60]∪[330,360]、s_in∈[0.25,0.85]、亮度>30，且**输出饱和度至少保留
输入的 55%**（否则去饱和表的 hue 抖动会被误记成偏红），取 16 张照片的中位数。

### 五、根因：warm_guard 削不动肤色

`gen_luts.py` 第 8 步的暖色保护：

```python
if s > 0.30 and v > 0.14 and (h <= 50 or h >= 330):
    w = ((s - 0.30) / 0.70) ** 0.7
    r -= (r - g) * wg * w
```

在典型肤色 `(200,150,130)` 上算：s=0.35、h=17°。

- `w = ((0.35-0.30)/0.70)^0.7 = 0.146`
- `wg = 0.30` ⇒ 实际只削 `0.196 × 0.30 × 0.146 = 0.0086` ≈ **2.2 级**
- 要把 -7.6° 修到 -3°，需要削 **21 级**

**差一个数量级。** 门槛从 s=0.30 起算，而肤色正好卡在这个门槛上 ——
真实照片里占面积最大的暖色区，恰恰是保护最弱的地方。

参数扫描（真实照片实测）：

| 设置 | kchrome64 的 dHue | 饱和增益 dSat |
|---|---|---|
| 现状 wg=0.30 | -3.17° | +0.176 |
| wg=0.45 | -0.85° | +0.157 |
| wg=0.60 | +1.79° | +0.136 |
| wg=0.90 | +11.15° | +0.061 |

wg=0.45 对 kchrome64 / xpro / rsx200 有效（拉到 ±1.6°），但对 kchrome25、velvia50
几乎无效 —— 因为这两张表的暖色区 `r-g` 超量大，被削幅上限挡住，且饱和结构不同。

**提高 wg 会带来副作用**：旧版 `h<=50 or h>=330` 是硬判，边界处 R 一步跳变。
wg=0.45 时全部表的相邻格点跳变从 4.5 涨到 6.7，部分表变非单调。
必须先改成平滑窗口才能提强度（已在 `gen_luts.py` 里备好参数开关，默认关闭）。

### 九、第二轮：暖色保护重做 + 全量重建

第一轮定位到根因（§五）后，本轮把 `gen_luts.py` 第 8 步的暖色保护重写并全量重建，

#### 9.1 改了什么

| 参数 | 旧 | 新 | 作用 |
|---|---|---|---|
| `warm_huew` | 0（硬判 `h≤50 \|\| h≥330`） | **60**（余弦淡出） | 边界不再一步跳变 —— 这是 wg 能提上去的前置条件 |
| `warm_vsoft` | False | **True** | 权重 ×min(1,v/0.14)，消除「(32,0,0) 不削、(48,0,0) 削」的红轴亮度倒挂 |
| `warm_cut` | 1.0（不封顶） | **0.15** | 封顶改按**该点 R 的比例**，不按绝对量；绝对量在低亮度处会压平红轴 → 非单调 |
| `WARM_GUARD` | 0.30 | **0.45** | 全局强度 |

5 张重灾表单独拉满 —— `warm_guard 0.90 / smin 0.15 / pow 0.45 / huew 70 / cut 0.35`：
`kodak_kchrome25`、`kodak_kchrome64`、`fuji_classicchrome`、`agfa_rsx200`、`ricoh_xpro`。

#### 9.2 结果：dHue 全部进 ±3°

16 张真实照片、暖色区中位（负 = 偏红；>±3° 可辨，>±5° 明显）：

| 表 | dHue 前 → 后 | dSat 前 → 后 | 暖区亮度 dY 前 → 后 |
|---|---|---|---|
| `kodak_kchrome25` | **-7.57° → -2.33°** | +0.141 → +0.120 | -0.295 → -0.332 |
| `kodak_kchrome64` | **-4.70° → +0.66°** | +0.092 → +0.049 | -0.190 → -0.213 |
| `ricoh_xpro` | **-6.33° → +0.79°** | +0.062 → +0.021 | -0.162 → -0.217 |
| `fuji_classicchrome` | **-3.80° → +1.69°** | -0.172 → -0.190 | +0.085 → +0.059 |
| `agfa_rsx200` | **-3.46° → +2.19°** | -0.072 → -0.112 | -0.044 → -0.077 |

**代价**：暖区饱和度少收 2-4 个百分点，亮度再暗 2-6 个百分点（表右列）。
这是「削 R 换色相」的固有成本 —— 对正片/克罗姆这类本来就厚的片子，方向是对的。

视觉证据：`_preview/fix_kchrome25_face.png`（`SAM_0026` 脸部三联）——
同一块肤色，原图 / 修前 / 修后的中位色相 **19.5° → 24.1°**，红橙转回暖黄；
肉眼看修前整张脸发橙红，修后是正常的暖肤色。

#### 9.3 试过但否掉的方案：`warm_lift`（还 G 保亮度）

数学上更优：削掉的 R 按 `.299/.587 ≈ 0.51` 还给 G，ΔY ≈ 0，亮度完全守恒。
**但色相是 r、g 的比值函数，还 G 的杠杆效应太大**：`kodak_kchrome25` 从 -2.33° 直接冲到
**+12.64°**（约 29°/单位 lift），红翻成黄绿；要压回中性得把 wg 降到 1/3，饱和白丢。
参数保留（默认 0），代码里带削幅上限 `cut ≤ (r-g)/(1+lift)` 防越过中性，
将来给「绝对不能变暗」的表单独开。

#### 9.4 纠错：`samsung_a00/a01/a02` 不是垃圾表

上一轮体检把它们按 look 口径判成「非单调 + 动态范围 180-200」，
本轮核对 `LUT_UI_2026-10-18` §8.5：它们与机身原厂槽 A00/A01/A02
**md5 完全一致**（`134909c7` / `69a4ac46` / `3ac93837`），用途是「对照原厂风格」。
低反差、灰轴微非单调都是原厂冷调设计。`audit.py` 新增 **REF 档位**：
只核 black/crush/jump，不判 mono/dr/gray/white/hue。

同理 `warm_sepia` 的 `hue_err 168°` 是棕调表的必然结果，已随 `warm_*` 一起豁免。

## 4. 品牌色系复现：先修一个底层 bug，再按色彩特征验收

> 原文：`LUT_BRAND_LOOKS_2026-10-25.md`（已归档至 `docs/archive/`）

2026-10-25 晚。承接 本文 §3。
本文要报告一件不体面但必须说的事：**上一轮的色彩坐标是错的**，因此那一轮的
六轴结论需要撤回重写。修好之后才做出用户要的冷色/青绿/青橙/金黄与理光蓝、
佳能红、宾得正负逆冲。

### 一、底层 bug：sRGB→XYZ 矩阵乘反了

`similarity_audit.rgb_to_lab()` 把矩阵写成了"行是 RGB 系数"再转置一次，等于用了
转置矩阵。表现：

| 输入 | 错误结果 | 正确结果 |
|---|---|---|
| 纯白 (255,255,255) | L\*=107，a\*=−90.9 | L\*=100，a\*=0 |
| 中性灰 (128,128,128) | a\*=−54.5 | a\*=0 |
| 肤色 (232,190,170) | L\*=87.2，a\*=−55.2 | L\*=80.1，a\*=+12.1 |

中性灰和纯白算出巨大负 a\*，这个"色彩空间"根本不成立。它是个连续单调变换，
所以**距离的排序大体保留**（清理方向没错），但**所有色相/彩度的绝对值都是假的**。

因此上一轮"库是一条窄带，warmth 只有 0.4~11.8、没有偏冷的表"这个结论**作废**。
用正确空间重算：

| 轴 | 我上一轮报的 | 实际（非 gap_ 的原库） |
|---|---|---|
| warmth | 0.4 ~ 11.8 | **−2.3 ~ 11.0**（cool_arctic、fuji_eterna500 本来就是冷的）|
| saturation | 33.7 ~ 56.2 | **0 ~ 38.8** |
| green_mag | −66.7 ~ −33.6 | 改用 a\* 表示：**−2.0 ~ 2.2** |

#### 第二个 bug：两个指标测的是同一个量

`shadow_tint` / `high_tint` 原来在 L\*=0 和 L\*=100 处读 b\*。但 `grade()` 的
`endpoints = smooth(0,7,L)` 会在暗端把染色淡出、`protect_white` 在高光端淡出，
所以两处读数都是 0，两个指标同时退化成 `−b*(中灰)`——同一个数算了两遍。上一轮
"分离色调幅度都很小"的判断也由此而来。

改成在输入 45 / 128 / 210 三点读取，并补 `shadow_a` / `high_a` 两个量，四个量才真正独立
（`metrics.py`）。

### 二、原库的真实短板不在冷暖，在绿-品红轴

修正后的原库（不含 gap_）范围：

```
warmth      -2.3 .. 11.0
saturation   0.0 .. 38.8
contrast     0.6 .. 1.3
shadow_tint -10.7 ..  4.6
high_tint   -2.1 .. 11.7
shadow_a    -2.0 ..  2.2      <- 关键
high_a      -1.3 ..  2.5      <- 关键
```

**`shadow_a` 和 `high_a` 都只在一个极窄的正负 2 之内**——也就是说整个库几乎没有
刻意的绿偏或品红偏。这才是"理光蓝不蓝、佳能红不红"的坐标证据：不是冷暖不够，
是**色相方向几乎没被用过**。

旧的 ricoh_*/canon_*/cool_* 十二张表挤在同一格：

```
canon_landscape   warm 2.7  sat 53.5  contr 0.97  hiTw 2.8
ricoh_positive    warm 4.1  sat 50.7  contr 1.01  hiTw 1.9
cool_blue/cyan/mint/slate/steel  warm 0.4~2.7  sat 51~53  contr 0.87~0.95
```

同一个模板换了名字。所以它们被上一轮按距离清掉并不冤——**要做的是重做得有特征，
不是把旧表从归档里搬回来**。

### 三、两条硬约束（先探明，再设计）

写方案前先探参数的真实边界，否则又是在许做不到的愿。

**1. 蓝的"更青"与"更浓"在 sRGB 里互斥**

```
sat_hues{'240'}   C*     hue    a*
1.0              66.3   291.0  23.8
1.3              75.9   289.9  25.8
1.6              77.9   288.0  24.1   <- C* 峰值
2.0              74.8   285.8  20.4
2.6              71.4   283.5  16.7
```

色相往青走必须压低 a\*（引入绿），而绿一多蓝就不纯，C\* 必然回落到 78 以下。
**"理光蓝"因此锁定为"色相更青"，不是"更饱和"**——判据是 hue < 286、C\* > 64、a\* < 20。

**2. 高光染色量由"中灰与高光的 b\* 差"决定，不取决于高光绝对值**

```
mid_b=10 hi_b=13  ->  high_tint  3.1
mid_b= 6 hi_b=16  ->  high_tint  8.3
mid_b= 3 hi_b=18  ->  high_tint 12.5
mid_b= 0 hi_b=20  ->  high_tint 16.7
```

想让高光"金"就必须让中灰"不金"。所以金黄方案的暖度由**阴影段**承担，中灰几乎不加 b。

### 一、为什么换掉自建表

自建表走的是物理模型 + 风格目标反推（`film_physics.py` / `style_profiles.json`），能保证不越界、
不失真，但**没有原机受控样本**，片种间的差异被模型压小（前一轮已确认旧 13 表最近多对 ΔE00 1.4–1.7，
用户判为同质化）。外部 CLUT 是别人拿真胶片/官方色彩科学做的成品，片种指纹是现成的。

代价也很清楚：外部表的 S 曲线按「平坦输入」设计，压到已显示参考的 JPEG 上，暗部更容易压死。
`crush_pct` 因此普遍比自建表高——这是交换不是纯增益，见第四节。

### 二、解码：两个坑

#### 坑 1：G'MIC 的 Hald PNG 不是教科书布局

教科书 Hald 是 64×64 tile、tile 索引→B、x→R、y→G。按此解，与 G'MIC 自己的 13³ `.cube`
最大差 **250/255**——完全对不上。

实测（沿 x 找 R 的回归点，间距 64；沿 y 无回归点）确定真实映射为
`idx = y*512 + x`，tile 与通道的对应需另定。

#### 坑 2：拿 `.cube` 互校会给出「错的正确答案」

用 12 种候选（2 种数组序 × 6 种通道排列）扫，最佳是
`r = idx//4096, g = (idx//64)%64, b = idx%64`，对 13³ `.cube` 均差 **2.2/255**、最大 27.8/255
——残差量级正好是 13³ 重采样应有的，看起来完全成立。

**但它是错的。** G'MIC 的 PNG 与 `.cube` 用同一套（蓝最快的）顺序存储，两者互校时 R/B 同时
被换掉、误差相互抵消。用它导出的表，Portra 400 把 (208,48,48) 送成 (113,80,227)：红变蓝。

暴露路径只有两条，都不在解码环节：

1. `audit.py` 的 `hue_err`：全部彩色表 ~145°，而自建表是 5–12°。单看 jump/dr/black 全正常。
2. 摄影常识：Portra 400 必须把红送成红。

修正后 `r = idx%64`（红最快）、`g = (idx//64)%64`、`b = idx//4096`，Portra 400 给
(208,48,48)→(251,65,23)、(48,64,208)→(107,95,225)，六主色全部落回合理区，`hue_err` 降到 13–32°。

> 教训：**互相一致的两种编码不能互为基准**。R/B 互换是自洽变换，任何用同源数据做的回归都会
> 把它吸收掉。必须有外部锚点（真实照片的方向性，或原厂槽这类独立来源）。

#### 用 PNG 还是 `.cube`

`.cube` 是 13³（G'MIC 统一降采样过），PNG 是 64³。目标网格 17³，从 13³ 三线性上采会先丢信息
再补形状，陡的高光肩部尤其吃亏。所以走 PNG。13³ 的 `.cube` 仅用于布局反推的交叉验证。

- **“加性调色必然偏品红”错误。** `RGB+(0,-d,0)` 就能只降低绿；加性或乘性都须检验完整映射。棕褐、蓝调、分离色调不能仅因灰轴有色就判坏。
- **80.5%网格越界不等于成片污染比例。** 必须检查合法RGB经插值后的映射。灰轴投影也没保留恒等：33³合法RGB点最大通道误差41.02/255，大于旧逐通道裁切7.60。新边界单元线性外推保留恒等/灰度等仿射语义，但仍非任意非线性设计的完美标定。
- **同质化确实存在。** 按每档亮度强制归中性、统一黑白端点、相近曲线混合比例压小了区别。旧13表Portra400/Gold200的72探针中位ΔE00=1.66，Superia400/Vista100=1.43。
- **旧manifest取的是最近节点，非实际插值。** Ektar输入(210,180,70)在最终原生表实际重建约(219.07,159.04,9.05)，并非B=0；通道为0也不能单独证明失败或17³硬限制。
- **部署13表不等于逐一实拍验收。** 后批JPEG自动WB，前轮手动WB，不能称为同条件A/B。
- **光谱库不保证复刻。** [spectral_film_lut](https://github.com/JanLohse/spectral_film_lut)采用数字化曲线和光谱，也有数据缺项和简化假设。宾得、理光、佳能可以依据官方风格目标设计；精确复制需要受控原机样本，不能因没有H&D曲线就排除设计。
- **LUT输入已经是sRGB、gamma=2.2的断言未获证实。** 须分别测输出端响应和输入端相对曝光响应。

RGB直接当Cr/Cb/Y写入的格式错误有前轮受控实拍支持，见 [编码修复](LUT_FORMAT_AND_INPUT_2026-10-19_to_11-07.md)。OLED不是已证实根因。

`film_physics.py`已改为有效RGB33³求值、独立灰参考、浮点构建后一次原生量化，输出编码哈希。旧投影仅保留审计。外部`build_final_batch.py`输出新目录，在量化后按实际插值取探针，原13表保留作证据。

新12主方案分别声明影调、冷暖与选择性色相目标，配方开放；它们是参考风格设计，尚非原厂/胶片逐款实测复制。
